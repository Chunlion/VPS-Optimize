# Восстановление доступа и откат

Данное руководство используется для устранения уже возникших проблем: SSH отключен, межсетевой экран заблокирован по ошибке, повторное использование порта 443 поврежден, вход Nginx или Caddy/Nginx не может запуститься, сертификат не работает, панель невозможно открыть. Его цель — сначала восстановить контроль, а затем устранить основную причину.

Пути меню в этой статье написаны в формате «главное меню [копия нумерованного меню] -> [копия подномерного меню]», а команды быстрого доступа не записываются в каждый путь.

## сначала сделай три дела

1. Не закрывайте окно SSH, которое все еще прикреплено.
2. Не повторяйте одно и то же руководство по высоким рискам снова и снова.
3. Сначала определите, можете ли вы еще войти на сервер.

| Текущий статус | приоритетное действие |
|---|---|
| В настоящее время SSH все еще существует. | Сохранить окно, сначала создать резервную копию или проверить статус службы |
| Новый SSH не может подключиться, но старое окно все еще существует. | Восстановите SSH, брандмауэр или группу безопасности облака со старым окном. |
| Все SSH сломаны. | Войдите в систему, используя VNC/консоль восстановления облачного поставщика. |
| В систему можно войти, но 443 не работает. | Сначала проверка состояния, затем отдельная обработка в соответствии с входной службой, механизмом веб-обратный прокси и сертификатом. |
| Системы и сервисы находятся в беспорядке | Установите приоритет восстановления из резервной копии сценария или облачного снимка. |

## Минимальная проверка для входа в систему

Давайте сначала посмотрим на порт и неисправный сервис:

```bash
ss -lntp
systemctl --failed --no-pager
systemctl status ssh --no-pager || systemctl status sshd --no-pager
systemctl status nginx caddy x-ui --no-pager
```

Повторно введите:

```text
Главное меню [15 Обзор состояния служб]
Главное меню [13 Диагностика и освобождение портов]
```

Когда вам нужно перезапустить службу или проверить логи:

```text
Главное меню [15 Обзор состояния служб] -> [s Восстановление служб] -> [r Перезапустить основную службу]
Главное меню [15 Обзор состояния служб] -> [s Восстановление служб] -> [f Перезапустить службы со сбоями]
Главное меню [15 Обзор состояния служб] -> [s Восстановление служб] -> [l Просмотреть журналы служб]
```

Если это проблема с повторным использованием порта 443, приоритет:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [13 443 Проверка соединения]
```

Если вы готовы откатиться:

```text
Главное меню [16 Резервное копирование и откат конфигурации] -> [5 Просмотреть или изменить применённую конфигурацию]
Главное меню [16 Резервное копирование и откат конфигурации] -> [2 Просмотреть существующие резервные копии]
Главное меню [16 Резервное копирование и откат конфигурации] -> [3 Восстановить из резервной копии]
```

## SSH потерял связь

### явление

- Новый порт невозможно подключить.
- Время входа в систему истекло после изменения порта SSH.
- Не удалось войти в систему с открытым ключом или паролем.

### Если старое окно SSH все еще там

Сначала подтвердите фактическую привязку SSH:

```bash
ss -lntp | grep -E 'ssh|sshd'
systemctl status ssh --no-pager || systemctl status sshd --no-pager
```

Проверьте конфигурацию SSH:

```bash
sshd -t
grep -nE '^(Port|PasswordAuthentication|PubkeyAuthentication|PermitRootLogin)' /etc/ssh/sshd_config
```

Затем подтвердите двухслойный выпуск:

| Иерархия | что делать |
|---|---|
| Группа облачной безопасности | Выпустите новый порт SSH в консоли облачного поставщика. |
| Системный брандмауэр | Введите `Главное меню [8 Правила брандмауэра]`, чтобы освободить новый порт. |

Не закрывайте старое окно. Откройте новый локальный терминал для тестирования:

```bash
ssh -p НОВЫЙ_ПОРТ root@серверIP
```

### Если все SSH сломаны

Войдите в систему с помощью облачного провайдера VNC/Rescue Console и действуйте последовательно:

1. Убедитесь, что служба SSH запущена.
2. Освободите порт SSH.
3. Исправьте `/etc/ssh/sshd_config`.
4. Перезапустите службу SSH.
5. Откройте новый терминал для проверки входа.

Часто используемые команды:

```bash
systemctl restart ssh || systemctl restart sshd
sshd -t
ss -lntp | grep -E 'ssh|sshd'
ufw status numbered 2>/dev/null || firewall-cmd --list-ports
```

Если вы не уверены, что было изменено, сначала воспользуйтесь восстановлением облачных снимков. Резервное копирование сценария не может заменить полные снимки машины.

## Брандмауэр заблокирован по ошибке

### явление

- Привязка порта SSH в норме, но подключиться к Интернету невозможно.
- Доступ к веб-сайту или панели возможен локально, но доступ к Интернету невозможен.

### Проверить

```bash
ufw status numbered 2>/dev/null || true
firewall-cmd --list-all 2>/dev/null || true
ss -lntp
```

### Процесс

Прежде чем войти, подтвердите разрешение от группы безопасности облака:

```text
Главное меню [8 Правила брандмауэра]
```

Рекомендуемый приоритет:

```text
[1 Включить брандмауэр и разрешить текущие публичные порты]
```

Если вам нужно только добавить порты, выберите:

```text
[2 Разрешить порты вручную]
```

Не удаляйте текущий порт SSH. Отключение брандмауэра и удаление правил являются операциями с высоким риском, и сценарий запросит заглавную букву `YES`.

### Ограничение количества одновременных подключений к порту заблокировано по ошибке

`Главное меню [8 Правила брандмауэра] -> [5 Ограничение количества одновременных подключений к порту]` записывает дополнительные правила ограничения connlimit `iptables` / `ip6tables`, которые не эквивалентны правилам доступа к портам UFW/firewalld. Это ограничит количество одновременных подключений TCP на IP-адрес источника по общедоступному порту; если вы ограничиваете Интернет `443` и включаете повторное использование порта 443, вы можете ограничить только весь Интернет `443` и не можете быть точными для конкретного входящего соединения Xray/3x-ui, SNI, UUID или пользователя. Не выбирайте `[6 Отключить брандмауэр]` по ошибке.

Если вы все еще можете войти в меню, сначала перейдите:

```text
Главное меню [8 Правила брандмауэра] -> [5 Ограничение количества одновременных подключений к порту] -> [3 Просмотреть правила ограничения подключений]
Главное меню [8 Правила брандмауэра] -> [5 Ограничение количества одновременных подключений к порту] -> [2 Удалить ограничение подключений к порту]
Главное меню [8 Правила брандмауэра] -> [5 Ограничение количества одновременных подключений к порту] -> [5 Сохранить/проверить состояние после перезагрузки]
```

После того как сценарий удалит правило, он автоматически попытается обновить постоянный снимок; `[5]` используется для подтверждения того, был ли сохраненный файл синхронизирован. Если в системе нет существующего пути сохранения серии `netfilter-persistent`, `iptables-persistent` или RHEL для `iptables-services`, в меню появится сообщение о том, что текущее правило connlimit вступит в силу только во время этого запуска.

Если вход в меню невозможен, используйте VNC/Rescue Console для просмотра тегов правил сценария:

```bash
iptables -S INPUT | grep 'VPSO_CONN_LIMIT_PORT_'
ip6tables -S INPUT | grep 'VPSO_CONN_LIMIT_PORT_'
```

Удалите только одно правило, принадлежность которого подтверждена к этому сценарию и чей порт и номер соединения совпадают. Метод состоит в том, чтобы скопировать весь `-A INPUT... VPSO_CONN_LIMIT_PORT_порт...` в выходные данные, изменить `-A INPUT` в начале на `-D INPUT` и затем выполнить его; правило IPv6 использует `ip6tables` таким же образом. Не очищайте цепочки INPUT пакетно и не смешивайте правила выпуска UFW/firewalld и правила ограничения connlimit.

## 443 одновходная модификация

### явление

- Ни панель, ни подписку, ни сайт открыть невозможно.
- служба входа или механизм веб-обратный прокси не удалось запустить.
- Браузер 404, 502, ошибка сертификата.
- REALITY не может быть подключен.

### Первый раунд проверки

`8443`, `1443`, `40000` и `2096` в следующих командах и таблицах являются примерами портов; фактическая конфигурация зависит от текущей привязки службы и конфигурации, сохраненной сценарием.

```bash
ss -lntp | grep -E ':443|:8443|:1443|:40000|:2096'
systemctl status nginx --no-pager
systemctl status caddy --no-pager
systemctl status vpso-mux --no-pager
nginx -t
caddy validate --config /etc/caddy/Caddyfile
```

Затем введите:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [13 443 Проверка соединения]
```

### Не запускайте сначала первую конфигурацию повторно.

При добавлении нового веб-сайта, изменении внутреннего порта или пересмотре сертификата не следует повторно запускать первую конфигурацию. Обычно используемые входы:

| цель | путь меню |
|---|---|
| Добавить или удалить сайты | `Главное меню [19 Управление повторным использованием порта 443] -> [8 менеджмент Web домены / обратный прокси]` |
| Коммутатор Caddy/Nginx Механизм веб-обратный прокси | `Главное меню [19 Управление повторным использованием порта 443] -> [8 менеджмент Web домены / обратный прокси] -> [8 переключатель Web механизм обратного прокси]` |
| Перестроить конфигурацию | `Главное меню [19 Управление повторным использованием порта 443] -> [6 Повторно применить текущий режим входа]` |
| Изменить параметры панели/подписки/REALITY | `Главное меню [19 Управление повторным использованием порта 443] -> [10 Изменить параметры повторного использования порта 443]` |
| Caddy/Обслуживание сертификата | `Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов]` |
| Откат 443 конфигурации | `Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [6 откат 443 Конфигурация с повторным использованием порта 443]` |

### Не работает после переключения механизма обратный прокси веб-страниц Caddy/Nginx.

Конфигурация 443 управления сценариями регулируется `/etc/vps-optimize/sni-stack.env`. При переключении механизма веб-обратный прокси через `[19] -> [8] -> [8]` будут считаны сохраненные параметры панели, подписки, веб-сайта, сертификата, белого списка и серверной части для восстановления конфигурации целевого механизма; рукописная конфигурация Caddy/Nginx не будет подвергаться обратному анализу.

Если вы вручную меняли `/etc/caddy/conf.d`, `/etc/nginx/conf.d/vps_sni_web_*.conf` или созданные старым пунктом `[4 Обратный прокси]` файлы `/etc/nginx/conf.d/vps_proxy_*.conf`, сначала синхронизируйте параметры со скриптом через `[8 Управление веб-доменами/обратным прокси]` или `[10 Изменить параметры повторного использования порта 443]`, затем переключайте движок. Переход на локальный веб-прокси Nginx изолирует управляемую скриптом веб-конфигурацию Caddy 443; обратный переход изолирует локальную веб-конфигурацию Nginx. Повторное применение конфигурации 443 также изолирует старый публичный обратный прокси Nginx HTTPS, чтобы он не занимал порт `443`.

`ENTRY_MODE=xray-fallback` не поддерживает белый список веб-сайтов, независимо от того, выбирает ли локальный механизм обратного веб-прокси Caddy или Nginx. Причина в том, что после отката Xray локальный механизм обратного веб-прокси не может надежно получить реальный исходный IP-адрес клиента. Если вам нужен белый список Интернета, переключитесь на Nginx Stream или TCP Peek и нажмите `SNI + источник IP` limit на уровне входа в Интернет.

## Nginx Не могу встать.

### Распространенные причины

- `443` занят Apache, старым сервером Nginx, 3x-ui, Xray или устаревшей служба входа.
- Синтаксическая ошибка конфигурации `stream` для `/etc/nginx/nginx.conf`.
- Старая конфигурация обратного прокси-сервера Интернета HTTPS и конфигурация общей записи 443 дублируются.
- После выбора Nginx в качестве механизма веб-обратный прокси синтаксис `/etc/nginx/conf.d/vps_sni_web_*.conf` или путь сертификата являются ненормальными.

### Проверить

```bash
ss -lntp | grep ':443'
nginx -t
journalctl -u nginx -n 80 --no-pager
grep -R "listen.*443" /etc/nginx /etc/caddy 2>/dev/null
```

### Процесс

Целевой статус:

| компоненты | следует послушать |
|---|---|
| 443 Входные услуги | Nginx Stream, vpso-mux или Xray Основное входящее соединение, выберите одно из трех для привязки к Интернету `443` |
| Механизм веб-обратный прокси | Caddy или Nginx контролируют локальный HTTPS, например `127.0.0.1:8443`. |
| REALITY местный входящий | В режиме Nginx Stream/TCP Peek обычно это `127.0.0.1:1443`. |
| Панель 3x-ui | `127.0.0.1:40000` |

Если Nginx не может быть запущен после вытеснения старой конфигурации или включения механизма веб-обратный прокси, сначала подтвердите:

```bash
grep -E '^(ENTRY_MODE|WEB_PROXY_ENGINE|NGINX_LISTEN_ADDR|NGINX_LISTEN_PORT|CADDY_LISTEN_ADDR|CADDY_LISTEN_PORT)=' /etc/vps-optimize/sni-stack.env 2>/dev/null
grep -R "listen.*443" /etc/nginx/conf.d /etc/nginx/sites-enabled /etc/caddy 2>/dev/null
nginx -t
```

Повторно введите:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [15 изолировать старое Caddy Конфигурация]
Главное меню [19 Управление повторным использованием порта 443] -> [6 Повторно применить текущий режим входа]
```

## Механизм веб-обратный прокси не может запуститься или 502

### Распространенные причины

- Текущая синтаксическая ошибка конфигурации механизма веб-обратный прокси.
- На внутреннем порту нет службы.
- Обратный адрес написан неверно.
- Файл сертификата отсутствует или имеет неправильные разрешения.
- Nginx Неправильный метод записи сервера/расположения или путь сертификата локального веб-прокси.

### Проверить

```bash
grep -E '^(ENTRY_MODE|WEB_PROXY_ENGINE|PANEL_DOMAIN|CADDY_LISTEN_ADDR|CADDY_LISTEN_PORT)=' /etc/vps-optimize/sni-stack.env 2>/dev/null
caddy validate --config /etc/caddy/Caddyfile
systemctl status caddy --no-pager
journalctl -u caddy -n 100 --no-pager
nginx -t
systemctl status nginx --no-pager
journalctl -u nginx -n 100 --no-pager
ls -l /etc/nginx/conf.d/vps_sni_web_*.conf 2>/dev/null
curl -I http://127.0.0.1:40000/panel/
curl -I http://127.0.0.1:2096/sub/
```

### Процесс

| вопрос | путь меню |
|---|---|
| Просто синтаксис Caddy или проблема с перегрузкой. | `Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [12 Проверьте и перезагрузите Caddy]` |
| Nginx Обратный синтаксис локальной сети или проблема с перегрузкой | `Главное меню [19 Управление повторным использованием порта 443] -> [6 Повторно применить текущий режим входа]` |
| Нужно переключить веб-прокси Caddy/Nginx. | `Главное меню [19 Центр управления повторным использованием порта 443] -> [8 Управление веб-доменами/обратным прокси] -> [8 Переключить механизм веб-прокси]` |
| Внутренний порт или путь написаны неправильно. | `Главное меню [19 Управление повторным использованием порта 443] -> [10 Изменить параметры повторного использования порта 443] -> [1 Изменить порты и пути панели/подписки]` |
| Файл сертификата или символическая ссылка ненормальны | `Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [10 перестроить /root/cert символическая ссылка на сертификат]` |
| Я не знаю, что это за проблема | `Главное меню [19 Управление повторным использованием порта 443] -> [13 443 Проверка соединения]` |

## Сертификат не удался

### Сначала подтвердите

```bash
date -Is
dig +short A panel.example.com @1.1.1.1
dig +short AAAA panel.example.com @1.1.1.1
grep -E '^(WEB_PROXY_ENGINE|PANEL_DOMAIN|CADDY_LISTEN_ADDR|CADDY_LISTEN_PORT)=' /etc/vps-optimize/sni-stack.env 2>/dev/null
systemctl status nginx caddy --no-pager
journalctl -u caddy -n 100 --no-pager
journalctl -u nginx -n 100 --no-pager
```

Для токена Cloudflare требуется как минимум:

```text
Zone.Zone.Read
Zone.DNS.Edit
```

Сценарий использует Cloudflare DNS-01 для выдачи сертификата. Оранжевое облако не является непосредственной причиной сбоя при выпуске; переключение на серое облако здесь используется только для устранения проблем с каналом доступа в Интернет. Если выдача не удалась, вам следует сначала проверить разрешения токена, зону авторизации, распространение TXT `_acme-challenge`, время сервера и журналы acme.sh.

### обрабатывать запись

```text
Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [8 обновить Cloudflare API Token]
Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [9 Перевыпустить сертификат домена]
Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [13 Caddy/Сертификат проверка состоянияа в один клик]
```

Сохранение Caddy в названии меню является историческим названием; независимо от того, выбирает ли механизм веб-обратный прокси Caddy или Nginx, сертификат по-прежнему выдается `acme.sh + Cloudflare DNS API`, а `/etc/caddy/certs/${domain}.crt|key` и `/root/cert/${domain}.crt|key` продолжают использоваться.

Самый последний журнал ошибок acme может находиться по адресу:

```text
/root/cert/acme_last_error.log
```

Не публикуйте токен, закрытый ключ или полный ключ подписки публично.

## Панель невозможно открыть

### Быстрое решение

```bash
curl -I http://127.0.0.1:40000/panel/
curl -I https://panel.example.com/panel/
systemctl status x-ui --no-pager
```

| результат | судья |
|---|---|
| Локальный HTTP в норме, Интернет HTTPS недоступен. | Чаще всего это проблема со служба входа, механизмом веб-обратный прокси или сертификатом. |
| Локальный HTTP тоже не работает. | Сначала отремонтируйте 3x-ui или порт панели. |
| цикл перенаправления | 3x-ui все еще может включить встроенный HTTPS |
| 404 | Путь к панели и путь к механизму веб-обратный прокси несовместимы. |
| 502 | Механизм веб-обратного прокси-сервера не может найти бэкенд |

Общие входы:

```text
Главное меню [5 панель、Узлы и инструменты подписки] -> [3 панель SSL Ремонт]
Главное меню [19 Управление повторным использованием порта 443] -> [10 Изменить параметры повторного использования порта 443] -> [1 Изменить порты и пути панели/подписки]
Главное меню [19 Управление повторным использованием порта 443] -> [13 443 Проверка соединения]
```

## Подписка недоступна

### Проверить

```bash
curl -I http://127.0.0.1:2096/sub/
curl -I https://panel.example.com/sub/
curl -I https://panel.example.com/clash/
```

Ссылки на подписку не должны появляться:

```text
:2096
:40000
:8443
127.0.0.1
```

Обработка записи:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [11 Ссылка на подписку / External Proxy Советы]
Главное меню [19 Управление повторным использованием порта 443] -> [10 Изменить параметры повторного использования порта 443] -> [1 Изменить порты и пути панели/подписки]
```

## Соединение REALITY не выполнено.

### Проверить

```bash
ss -lntp | grep -E ':443|:1443'
openssl s_client -connect www.microsoft.com:443 -servername www.microsoft.com </dev/null
```

Ключевые моменты для подтверждения:

| Проект | Проверьте ключевые моменты |
|---|---|
| Локальная привязка REALITY | `127.0.0.1:1443` |
| клиентский порт | `443` |
| `dest` / `Target` | Внешний реальный сайт HTTPS |
| `serverNames` / `SNI` | Соответствует внешнему реальному сайту HTTPS. |
| домен узла | Только DNS / серое облако |

Обработка записи:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [10 Изменить параметры повторного использования порта 443] -> [2 Изменить REALITY локальный слушатель / маскировка SNI]
Главное меню [19 Управление повторным использованием порта 443] -> [6 Повторно применить текущий режим входа]
Главное меню [19 Управление повторным использованием порта 443] -> [13 443 Проверка соединения]
```

## Восстановление из резервной копии

### Полное резервное копирование скрипта

Подходит, когда в систему все еще можно войти и меню скриптов все еще можно открыть:

```text
Главное меню [16 Резервное копирование и откат конфигурации] -> [2 Просмотреть существующие резервные копии]
Главное меню [16 Резервное копирование и откат конфигурации] -> [3 Восстановить из резервной копии]
```

Резервные копии обычно находятся по адресу:

```text
/etc/vps-optimize/backups
```

### 443 Резервная копия повторного использования порта 443

Подходит для отката только входящих сервисов, обратного веб-прокси и конфигураций 443:

```text
Главное меню [19 Управление повторным использованием порта 443] -> [12 CF DNS / Caddy Обслуживание сертификатов] -> [6 откат 443 Конфигурация с повторным использованием порта 443]
```

Связанные пути:

```text
/etc/vps-optimize/backups/sni-stack_*
/etc/vps-optimize/sni-stack.last-backup
```

### облачный снимок

Подходит для таких ситуаций:

| ситуация | Предложения |
|---|---|
| SSH и VNC стабильно не подлежат ремонту | Восстановить облачный снимок |
| Невозможно запустить после переключения ядра | Восстановите облачный снимок или восстановите GRUB из режима восстановления. |
| Источник конфигурации неизвестен, и ремонт неоднократно не удался. | Вернуться к самому последнему явно доступному снимку |
| Повреждение каталога данных или базы данных | Сначала подтвердите резервное копирование, а затем рассмотрите снимки |

## Прежде чем отправить проблему

Первый запуск:

```text
Главное меню [15 Обзор состояния служб]
```

Создайте диагностическую информацию обратной связи в обзоре состояния. Обязательно десенсибилизируйте, прежде чем публиковать публично:

| содержание | Метод обработки |
|---|---|
| Cloudflare Token | Удалить |
| Закрытый ключ и закрытый ключ сертификата | Удалить |
| Пароль панели | Удалить |
| Ключ подписки | Удалить |
| домен реального пользователя | При необходимости можно заменить на `example.com`. |

Шаблон проблемы см. в [Отчет об ошибке VPS-Optimize](https://github.com/Chunlion/VPS-Optimize/blob/main/.github/ISSUE_TEMPLATE/bug_report.md)。
