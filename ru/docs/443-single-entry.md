# Порт 443: совместное использование и настройка

Эта инструкция объединяет панель, подписку, сайты и REALITY на одном публичном порту `443`. Все домены и порты из примеров замените своими значениями.

## Сначала выберите режим входа

Если вы не уверены, выбирайте **Nginx Stream**. Это рекомендуемый вариант для первой установки и самый простой для диагностики.

| Режим | Когда использовать | Рекомендация |
| --- | --- | --- |
| **Nginx Stream** | Первая установка или стабильная конфигурация | **Рекомендуется** |
| **TCP Peek + Splice** | Nginx Stream уже работает, нужен вариант TCP Peek | Переключить позже |
| **Xray Fallback** | Уже настроен основной вход Xray, который может занять публичный `443` | Расширенный вариант |

Одновременно публичный `443` может слушать только один сервис:

```text
Публичный 443 -> единственный сервис текущего ENTRY_MODE
Обычный HTTPS / сайты -> Caddy или Nginx -> локальный сайт
Панель / подписка -> Caddy или Nginx -> локальные HTTP-порты 3x-ui
REALITY-ноды -> локальный вход Xray / 3x-ui
```

Для обычной связки 3x-ui + сайт + REALITY выберите Nginx Stream и продолжайте.

## Полный пример значений

Ниже показано, что означает каждое поле. Это только пример — замените значения в рабочей конфигурации.

| Параметр | Пример | Назначение |
| --- | --- | --- |
| Домен панели | `panel.example.com` | Открытие панели 3x-ui в браузере |
| Домен ноды | `node.example.com` | Адрес ноды и адрес Hosts |
| Домен сайта | `site.example.com` | Обычный HTTPS-сайт |
| Цель REALITY | `www.example.org` | Маскирующий HTTPS-сайт; пример |
| Локальный порт панели | `40000` | 3x-ui слушает только на VPS |
| Локальный порт подписки | `2096` | Подписка доступна только локально |
| Локальный порт REALITY | `1443` | Локальный вход Xray / 3x-ui |
| Backend сайта | `127.0.0.1:3000` | Программа сайта за входом |

С этими значениями панель открывается по `https://panel.example.com/panel/`, подписка — по `https://panel.example.com/sub/`, а нода доступна как `node.example.com:443`. Порты `40000`, `2096`, `1443` и `3000` не должны быть открыты в Интернет.

Разделяйте три вида значений:

- `panel.example.com` и `node.example.com` — публичные имена для браузера и клиентов;
- `127.0.0.1:40000`, `127.0.0.1:2096` и `127.0.0.1:1443` — локальные адреса внутри VPS;
- `serverName` REALITY — маскирующая цель, например `www.example.org`, а не домен панели и не домен ноды.

## Подготовка перед установкой

### Домены и DNS

- Подготовьте домен панели и домен ноды, например `panel.example.com` и `node.example.com`.
- Направьте их на VPS у своего DNS-провайдера.
- Для REALITY `serverName` / `target` лучше использовать стабильный HTTPS-сайт, доступный напрямую и без защиты CDN. Если CDN-домен необходим, после установки включите [защиту трафика REALITY fallback](#защита-трафика-reality-fallback); без неё неудачные REALITY-подключения могут превратить сервер в CDN-ретранслятор и расходовать трафик.
- Не закрывайте текущую SSH-сессию. Разрешите SSH и TCP `443` в облачной группе безопасности и системном firewall.

Распределите домены так:

| Домен | Куда указывает DNS | Где используется |
| --- | --- | --- |
| `panel.example.com` | Публичный IP VPS | Панель и Web-прокси |
| `node.example.com` | Публичный IP VPS | Нода и адрес Hosts |
| `www.example.org` | Адрес самого целевого сайта | `serverName` / `target` REALITY |

Домены панели и ноды могут проходить через CDN, если это нужно для доступа. Для цели REALITY лучше выбрать сайт без CDN и не подставлять туда домен ноды.

### Cloudflare DNS API (если используется Cloudflare)

VPS-Optimize использует `acme.sh + Cloudflare DNS API` для сертификатов. Создайте Token только с правом изменения DNS в нужной зоне и не публикуйте его. Проверка DNS-01 позволяет скрипту выпустить сертификат для Web-прокси; панели 3x-ui и подписке не нужны отдельные публичные сертификаты.

### SSH и резервная копия

Перед изменением владельца порта `443` оставьте открытой SSH-сессию и создайте резервную копию. Если провайдер предоставляет консоль, убедитесь, что она доступна. Не выполняйте первую настройку `443`, рассчитывая на единственное соединение, которое может прерваться.

### Проверка порта 443

На VPS выполните:

```bash
ss -lntp | grep ':443'
```

Если `443` уже занят Nginx, Caddy или другой программой, запишите, для чего она используется. Скрипт проверит конфликт при переключении, но не сможет решить за вас, что нужно заменить.

## Установка по шагам

### 1. Установите 3x-ui на локальный адрес

Во время установки 3x-ui:

1. Для сертификата панели выберите `Skip SSL (advanced — behind reverse proxy / SSH tunnel only)`.
2. В качестве IP прослушивания укажите `127.0.0.1`.
3. Выберите порт и путь панели и сохраните их для настройки обратного прокси. Для примера можно указать:

   ```text
   Порт панели: 40000
   Путь панели: /panel/
   ```

   Если установщик не предлагает выбрать путь, используйте показанный им путь.

После этого панель будет доступна через общий `443`, а не через отдельный публичный порт.

После установки не используйте `http://IP-сервера:40000` как постоянный адрес. Сначала завершите настройку `443`, затем открывайте `https://panel.example.com/panel/` или фактический путь панели.

Если в настройках панели остались поля файла сертификата и ключа, очистите оба. Публичный HTTPS обрабатывает Caddy или Nginx, а 3x-ui должен предоставлять только локальную HTTP-страницу.

### 2. Настройте локальную подписку

Страница подписки 3x-ui настраивает только локальный backend. Публичный URL состоит из домена панели и URI-пути:

- адрес прослушивания: `127.0.0.1`;
- домен прослушивания: оставьте пустым;
- порт прослушивания: свободный локальный порт, например `53541` на снимке;
- URI-путь: используйте свой путь, например `/sublinkqq/`; `/sub/` и `/clash/` — примеры путей;
- Reverse Proxy URI: `https://panel.example.com/sublinkqq/`, то есть `https://домен панели + URI-путь`;
- не указывайте `node.example.com` и не выпускайте для подписки отдельный публичный сертификат.

По примеру локальные параметры подписки выглядят так:

```text
Адрес прослушивания: 127.0.0.1
Домен прослушивания: оставить пустым
Порт прослушивания: 53541
URI-путь: /sublinkqq/
Reverse Proxy URI: https://panel.example.com/sublinkqq/
```

В этом примере пользователь открывает `https://panel.example.com/sublinkqq/`; `53541` — внутренний порт VPS и не должен появляться в публичной ссылке. Если URI-путь — `/sub/`, URL подписки будет `https://panel.example.com/sub/`.

Если в настройках подписки есть поля сертификата и ключа, также очистите их. Иначе 3x-ui может попытаться запустить второй HTTPS-сервис на локальном порту.

### 3. Настройте вход REALITY

Создайте или измените вход VLESS REALITY в 3x-ui:

- адрес прослушивания: `127.0.0.1`;
- локальный порт, например `1443`, но не публичный `443`;
- транспорт: TCP;
- безопасность: REALITY;
- `serverName` / `target`: подготовленный реальный HTTPS-сайт;
- `serverNames`: тот же SNI;
- отпечаток: обычно подходит `chrome`;
- `Fallbacks` оставьте пустым, если вы специально их не настраиваете.

По примеру важные поля будут такими:

```text
Адрес прослушивания: 127.0.0.1
Порт прослушивания: 1443
serverName / target: www.example.org
serverNames: www.example.org
Fingerprint: chrome
```

UUID, ключи и shortId создайте кнопкой генерации в 3x-ui; не копируйте чужие примеры. Назовите вход, например, `VLESS-REALITY`, чтобы потом легко выбрать его в Hosts.

В ссылке ноды должны использоваться домен ноды и порт `443`, а не `127.0.0.1:1443`.

### 4. Запустите мастер настройки 443

Откройте в главном меню:

```text
[19 Port 443 Reuse Management] -> [2 Install / switch 443 entry mode]
```

Для первой установки:

1. Выберите **Nginx Stream**.
2. Выберите Caddy или Nginx для Web-прокси; при сомнениях оставьте значение по умолчанию.
3. Укажите домен панели, домен ноды и REALITY SNI.
4. Для панели укажите backend `127.0.0.1:40000`, для подписки — `127.0.0.1:2096`.
5. Для нового сайта укажите `127.0.0.1` и порт, например `3000`. Если сайт работает в Docker, опубликуйте контейнерный порт на loopback хоста (например `127.0.0.1:3000:3000`), а в мастере укажите порт хоста `3000`.
6. Перед сохранением проверьте все домены и порты.

Перед сохранением скрипт проверяет доступность backend. Если проверка не пройдена, исправьте адрес или порт. Не открывайте backend напрямую в Интернет.

### 5. Свяжите домен ноды с входом в 3x-ui

После завершения мастера вернитесь в 3x-ui:

- проверьте, что панель слушает `127.0.0.1`;
- проверьте, что подписка слушает `127.0.0.1`, домен прослушивания пуст, а Reverse Proxy URI состоит из домена панели и URI-пути;
- в 3x-ui v3.4.0 и новее откройте `Hosts` и добавьте Host;
- в 3x-ui v3.4.0 и новее заполните Host по примеру: выберите вход VLESS REALITY с адресом `127.0.0.1:1443`, укажите адрес `node.example.com`, порт `443`, а Security / SNI / Fingerprint / ALPN оставьте такими же, как во входе и клиенте (`REALITY`, `www.example.org`, `chrome` и фактический ALPN);
- в 3x-ui v3.3.1 и старше откройте `External Proxy` во входе REALITY, оставьте тот же тип, укажите адрес `node.example.com` и порт `443`; `127.0.0.1:1443` сюда не вводите;
- скопируйте ссылку ноды и убедитесь, что в ней стоят домен ноды и порт `443`.

В Host поле «адрес» означает публичный домен ноды, а не локальный адрес. Поле «вход» связывает этот домен с локальным REALITY. Правильный результат:

```text
Адрес клиента: node.example.com
Порт клиента: 443
Адрес Hosts: node.example.com
Порт Hosts: 443
REALITY слушает: 127.0.0.1:1443
SNI REALITY: www.example.org
```

Если в ссылке остался `127.0.0.1:1443` или `node.example.com:1443`, сначала исправьте Hosts / External Proxy.

### 6. Проверьте работу и сделайте резервную копию

Откройте домен панели и URL подписки в браузере, затем проверьте ноду. После успешной проверки создайте резервную копию конфигурации.

На VPS можно выполнить проверки, которые ничего не меняют:

```bash
ss -lntp | grep -E ':(443|40000|2096|1443)'
curl -I https://panel.example.com/panel/
curl -I https://panel.example.com/sub/
```

Публичным должен быть только общий `443`; остальные примерные порты должны слушать `127.0.0.1`. Пути замените на те, что показывает ваша панель.

Если панель не открывается, сначала проверьте локальные порты и текущий режим входа. См. [Диагностика и восстановление](443-single-entry-troubleshooting.md).

## Переключение режимов и откат

### TCP Peek + Splice

TCP Peek принимает решение по SNI в начале соединения и использует лёгкий разветвитель. Это не новая настройка панели: **процесс настройки такой же, как для Nginx Stream**. Сначала завершите установку выше, затем выполните:

```text
[19 Port 443 Reuse Management] -> [2 Install / switch 443 entry mode] -> [3 TCP Peek + Splice]
```

Скрипт проверит зависимости, порты и доступность backend. Не закрывайте SSH, пока новый режим не проверен.

### Xray Fallback

Выбирайте этот режим только при уже настроенном основном входе Xray, который должен владеть публичным `443`. Xray принимает `443`, а обычный HTTPS передаёт выбранному Web-прокси Caddy или Nginx. Меню SNI-маршрутов скрипта не предназначено для управления несколькими входами Xray в этом режиме.

### Откат последнего переключения

При проблемах выполните:

```text
[19 Port 443 Reuse Management] -> [7 Roll back the previous entry-mode switch]
```

Затем снова проверьте домен панели, ссылку ноды и результат `ss -lntp | grep ':443'`.

## Обычное обслуживание

### Домены Web и обратный прокси

Используйте:

```text
[19 Port 443 Reuse Management] -> [8 Manage Web domains / reverse proxy]
```

Для смены Caddy и Nginx выберите `[8 Switch Web reverse-proxy engine]`. Домены и сертификаты общие для обоих вариантов; перед переключением проверьте backend.

Полный путь:

```text
[19 Port 443 Reuse Management] -> [8 Manage Web domains / reverse proxy] -> [8 Switch Web reverse-proxy engine]
```

Скрипт заново создаёт конфигурацию выбранного механизма и сохраняет существующие домены, сертификаты и backend. Не запускайте параллельно другую ручную конфигурацию Caddy/Nginx, которая может занять тот же порт.

При добавлении сайта заполняйте поля по порядку: домен, адрес backend, порт backend. Для программы на `127.0.0.1:3000`:

```text
Домен: site.example.com
Адрес backend: 127.0.0.1
Порт backend: 3000
```

Затем откройте `https://site.example.com` в браузере. Если программа работает в контейнере, сначала опубликуйте её на loopback хоста, а не используйте имя, доступное только внутри контейнера.

### Как заполнять URL обратного прокси

Этот раздел относится только к отдельно развёрнутому инструменту подписок, например SublinkPro или Sub-Store. Он не относится к подписке 3x-ui выше: для неё всегда используется `https://panel.example.com + URI-путь`.

Для отдельного инструмента сначала направьте `tool.example.com` на VPS, затем добавьте домен и backend через управление Web-доменами/обратным прокси в скрипте. Только после этого скрипт настроит Web-вход и сертификат. Этот домен не добавляется в `Hosts` ноды и не относится к маршрутизации REALITY SNI.

Для отдельного инструмента различайте два поля:

| Где заполнять | Правильный пример | Не вводить |
| --- | --- | --- |
| В меню скрипта «Веб-сайт/обратный домен» | `tool.example.com` | `https://tool.example.com/`, `127.0.0.1:3000` |
| В отдельном инструменте: `External URL` / `Public URL` / `Base URL` / URL обратного прокси | `https://tool.example.com/` | `http://127.0.0.1:3000/`, `https://tool.example.com:3000/` |
| В меню скрипта «Адрес backend» | `127.0.0.1` | `https://tool.example.com/` |
| В меню скрипта «Порт backend» | `3000` | `443`, если backend действительно не слушает 443 |

По примеру заполнение выглядит так:

```text
Меню скрипта:
  Веб-сайт/обратный домен: tool.example.com
  Адрес backend: 127.0.0.1
  Порт backend: 3000

Инструмент подписки:
  URL обратного прокси / External URL: https://tool.example.com/
```

Пользователь открывает `https://tool.example.com/`, а VPS-Optimize передаёт запрос на `127.0.0.1:3000`. Публичный URL содержит `https://` и домен; обычно `:443` указывать не нужно. Адрес и порт backend задаются только в настройках обратного прокси скрипта.

Если инструмент опубликован во вложенном пути, например `https://tool.example.com/app/`, укажите полный URL вместе с `/app/`. После сохранения откройте именно этот адрес и проверьте, что создаваемые ссылки подписки используют `https://tool.example.com/`, без `:3000`, `:2096` и `127.0.0.1`. Для SublinkPro, Sub-Store и похожих инструментов см. [Подключение сервисов подписок](../tutorials/02-subscription-tools-caddy-nginx-reverse-proxy-443-single-entry.md).

### Белый список IP для Web

Белый список действует на сайты и панель, но не на трафик REALITY. В режимах `nginx-stream` и `tcp-peek` используйте `[4] -> [5 Domain IP allowlist]`. Из управления Web-доменами доступен путь:

```text
[19 Port 443 Reuse Management] -> [8 Manage Web domains / reverse proxy] -> [5 Manage domain IP allowlist]
```

В режиме `xray-fallback`, независимо от выбора Caddy или Nginx в качестве локального Web-прокси, белый список относится только к Web-доменам и не является проверкой REALITY.

## Защита трафика REALITY fallback

Если SNI REALITY указывает на CDN-домен, включите доступные меры:

1. **Фильтрация SNI** — разрешены только зарегистрированные Web-домены, SNI-маршруты и REALITY SNI; неизвестный SNI отбрасывается.
2. **Ограничение fallback** — ограничиваются только соединения, не прошедшие проверку REALITY и отправленные в fallback.

Nginx Stream и TCP Peek поддерживают обе меры. В Xray Fallback нет переднего фильтра SNI, но можно использовать ограничение fallback. Фильтрация SNI не заменяет ключи REALITY и обычную проверку клиента.

Если возможно, выбирайте для REALITY обычный HTTPS-сайт без CDN: так ошибка в настройках с меньшей вероятностью приведёт к лишнему расходу трафика.

Откройте защиту в меню:

```text
[19 Port 443 Reuse Management] -> [17 REALITY fallback traffic protection]
```

Основные действия:

1. `[1] Enable strict SNI gate` — разрешать только зарегистрированные SNI в Nginx Stream / TCP Peek.
2. `[3] Resynchronize the current SNI list` — выполнить после добавления домена или маршрута.
3. `[4] Set REALITY fallback rate limits` — ограничивать только соединения, не прошедшие проверку REALITY; скрипт создаёт случайные значения и запрашивает подтверждение.
4. `[5] Clear REALITY fallback rate limits` — вернуть поведение Xray по умолчанию; также требуется подтверждение.

Изменение лимитов перезапускает панель или Xray. Не выполняйте его во время важной передачи данных и сохраните созданную резервную копию. Для цели REALITY без CDN обычно достаточно SNI-фильтрации, а лимит fallback не обязателен.

Список строгой фильтрации SNI создаётся из зарегистрированных Web-доменов, SNI-маршрутов и SNI REALITY. После добавления домена или изменения SNI сохраните настройки и выполните `[3] Resynchronize the current SNI list`; иначе новое имя может быть отклонено как неизвестное. Фильтрация не проверяет UUID, ключи и другие данные REALITY.

### Несколько входов REALITY

Да, но используйте **Nginx Stream** или **TCP Peek + Splice**. Эти режимы распределяют публичный `443` по нескольким локальным входам через SNI. `xray-fallback` такое распределение нескольких SNI не поддерживает.

Пример:

| Вход | Локальное прослушивание 3x-ui | SNI клиента | Маршрут 443 |
| --- | --- | --- | --- |
| `VLESS-REALITY-A` | `127.0.0.1:1443` | `sni-a.example.net` | `sni-a.example.net -> 127.0.0.1:1443` |
| `VLESS-REALITY-B` | `127.0.0.1:2443` | `sni-b.example.net` | `sni-b.example.net -> 127.0.0.1:2443` |

Порядок действий:

1. Создайте оба входа REALITY в 3x-ui, каждому задайте отдельный локальный порт и отличающийся SNI. Скрипт только записывает маршруты и не создаёт и не изменяет входы 3x-ui.
2. Оставьте режим Nginx Stream или TCP Peek.
3. Откройте `[19 Port 443 Reuse Management] -> [15 Xray inbound management]` и добавьте для каждого входа запись `SNI -> локальный адрес -> локальный порт`.
4. Откройте `[19 Port 443 Reuse Management] -> [17 REALITY fallback traffic protection] -> [4 Set REALITY fallback rate limits]`. Меню покажет все входы REALITY. За один запуск изменяется только выбранный вход, поэтому для защиты двух входов выполните действие дважды.
5. После добавления или изменения SNI выполните `[3] Resynchronize the current SNI list`.

Ограничение fallback сохраняется отдельно для каждого входа: это не общий переключатель и не ограничение на пользователя. У каждого входа должен быть свой локальный порт и свой SNI; включение для входа A не защищает вход B. Сейчас нет пакетной настройки лимитов для всех входов, поэтому каждый вход нужно выбирать и настраивать отдельно. Строгий SNI-фильтр общий для входа и охватывает все зарегистрированные SNI. Если 3x-ui использует PostgreSQL, скрипт не поддерживает ограничение fallback, чтобы не изменять удалённую базу данных; функция доступна только для локального SQLite 3x-ui.

В режиме `xray-fallback` внутри Xray могут существовать несколько входов, но публичным `443` владеет один основной вход Xray; скрипт не распределяет несколько SNI по нескольким локальным входам. Если несколько входов должны использовать один `443`, переключитесь на Nginx Stream или TCP Peek + Splice.

## Проверка и диагностика

1. Выполните `ss -lntp | grep ':443'` и убедитесь, что публичным `443` владеет только текущий вход.
2. Откройте домен панели и URL подписки в браузере.
3. Проверьте ноду по ссылке с доменом ноды и портом `443`.
4. Убедитесь, что SNI REALITY совпадает с выбранным целевым сайтом.
5. При `403/401` сначала проверьте Web-белый список, CDN/WAF и Host/SNI; при `502` — адрес и порт backend; при тайм-ауте — firewall, облачную группу безопасности и прослушивание `443`.
6. Для проверки входа, сертификатов, Web и Xray используйте `[19 Port 443 Reuse Management] -> [13 Port 443 connection health check]`; для публичных DNS/TCP/TLS-проверок — `[14 Port 443 network access test]`.
7. При ошибке откройте [Диагностика и восстановление](443-single-entry-troubleshooting.md), а сведения о режимах — в [Режимах входа и принципах работы](443-tcp-peek-engine.md).

## Чего не следует делать

- Не открывайте панель 3x-ui, подписку и backend напрямую в Интернет.
- Не запускайте два сервиса на публичном `443` одновременно.
- Не используйте домен панели, домен ноды или локальный адрес как REALITY-цель.
- Не переключайте режим без рабочей SSH-сессии и резервной копии.
- Не переносите домены, порты и пути из примеров в рабочую конфигурацию без изменений.
