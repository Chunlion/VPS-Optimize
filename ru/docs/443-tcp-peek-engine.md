# Реализация TCP Peek для общего порта 443

В этой статье описываются три 443 однозаходных реализации VPS-Optimize: стабильная реализация по умолчанию Nginx Stream, реализация одинаковой конфигурации TCP Peek + Splice / vpso-mux, специальная резервная реализация Xray.

`panel.example.com`, `site.example.com`, `node.example.com`, `SERVER_IP`, `8443`, `8444` и `1443` в данном примере являются примерными значениями и используются только для иллюстрации взаимосвязи ссылок. Во время фактического развертывания замените его реальным именем домена, IP-адресом сервера и портом, на котором в данный момент сохранен сценарий.

## общие границы конфигурации

Три режима входа используют один набор общей конфигурации:

- Имена веб-доменов, сопоставления серверной части механизма веб-обратный прокси и сертификаты являются общими; белый список веб-страниц используется только Nginx Stream и TCP Peek.
- Сертификат по-прежнему использует существующий процесс `acme.sh + Cloudflare DNS API`, не содержит модуль Caddy DNS и не использует `xcaddy`.
- Белый список веб-сайтов защищает только имена веб-доменов и не используется для ограничения трафика узлов Xray.
- Механизм обратного веб-прокси на общем точка входае 443 может выбрать Caddy или Nginx, и та же конфигурация будет повторно использоваться при переключении режимов точки входа.
- При использовании Nginx Stream или TCP Peek белый список Интернета вступает в силу как `SNI + источник IP` на входном уровне; `xray-fallback` не позволяет добавлять, сохранять или применять белый список веб-страниц независимо от того, выбрано ли Caddy или Nginx локальное создание локального веб-сайта.
- Только одна служба может прослушивать публичный порт `443`: `nginx`, `xray` или `vpso-mux`.
- Если `/etc/vps-optimize/sni-stack.env` не имеет `ENTRY_MODE`, он будет обработан как совместимый с `nginx-stream`.
- `engine` из `ENTRY_MODE` и `/etc/vps-optimize/443-engine.conf` записываются одинаково в `nginx-stream`, `xray-fallback` и `tcp-peek`. `nginx_stream`, `xray_fallback` и `tcp_peek`, написанные в старой версии, зарезервированы только как псевдонимы, совместимые по чтению; одно простое назначение будет автоматически перезаписано под новым именем. Если его невозможно безопасно перезаписать, страница состояния будет продолжать запрашивать.

Общие пути меню:

```text
Главное меню [19 443 центр управления общим входом]
  -> [2] Первая настройка/установка 443 единственный вход
  -> [3] переключиться на Nginx Stream режим
  -> [4] переключиться на Xray Fallback режим
  -> [5] переключиться на TCP Peek + Splice режим
  -> [7] Откатить последнее переключение режима входа
  -> [16] Посмотреть TCP Peek + Splice Статус / 8444 Предполетная подготовка
  -> [17] TCP Peek проверка правил маршрутизации
  -> [18] Посмотреть TCP Peek + Splice Журнал
```

Информацию о конкретных методах заполнения панели 3x-ui, подписки и входящего Xray см. в разделе «Быстрая проверка конфигурации режима трех входов 3x-ui» в [443 Учебное пособие по маршрутизация с одним входом](443-single-entry.md). Вот первый вывод:

| ENTRY_MODE | Как контролировать 3x-ui/Xray | Наиболее важные соображения при переключении |
| --- | --- | --- |
| `nginx-stream` | Панели, подписки и входящее подключение Xray прослушивают локальный порт `127.0.0.1`. | 3x-ui/Xray Не занимайте напрямую сеть общего пользования `443`. |
| `tcp-peek` | То же, что `nginx-stream`, но по-прежнему локальный порт. | Процесс настройки тот же; публичный порт `443` меняется только с `nginx` на `vpso-mux` |
| `xray-fallback` | Требуется основное входящее соединение 3x-ui/Xray для привязки к Интернету `443` и возврата к локальному порту механизма обратного веб-прокси. | Прежде чем вернуться в другие режимы, основной входящий Xray необходимо переместить из публичный порт `443`. |

## Стабильная реализация Nginx Stream по умолчанию

Nginx Stream — стабильный режим по умолчанию. Публичная сеть `443` контролируется Nginx stream, а `ssl_preread` используется для чтения SNI в TLS ClientHello, но TLS не завершается и трафик не расшифровывается.

```text
Публичная сеть 443
  -> Nginx stream ssl_preread
  -> panel/site/sub SNI  -> Caddy/Nginx местный Web обратный прокси TLS
  -> Xray/REALITY SNI   -> Xray/3x-ui локальное входящее подключение
  -> unknown SNI        -> По умолчанию Xray/REALITY бэкенд
```

Эта реализация имеет наиболее полный охват и подходит в качестве долгосрочной записи по умолчанию. Он отвечает за стабильный доступ к механизму веб-обратный прокси REALITY, панелям, подпискам, веб-сайтам, белым спискам веб-страниц и процессам отката.

## Реализация TCP Peek + Splice/vpso-mux

TCP Peek + Splice / vpso-mux и Nginx Stream используют один и тот же набор из 443 общих конфигураций записей. Нет необходимости создавать новый набор имен веб-доменов, сертификатов, серверных частей веб-обратного прокси-сервера, белых списков веб-сайтов и записей маршрутизации Xray SNI; Панели 3x-ui, подписки и входящие соединения Xray по-прежнему заполняются в соответствии с локальными привязками. При первом использовании сначала запустите `Главное меню [19 443 Общий центр управления входом] -> [16] Посмотреть TCP Peek + Splice Статус / 8444 Проверьте перед переключением`, чтобы убедиться, что `vpso-mux` может запускаться и пересылаться в `8444`; затем запустите `[17] TCP Peek Проверка правил маршрутизации`. Только когда пользователь впоследствии выполнит `[5] переключиться на TCP Peek + Splice режим`, Интернет `443` будет переключен с Nginx Stream на `vpso-mux`.

`vpso-mux` использует `MSG_PEEK` для просмотра SNI в TLS ClientHello без использования первого пакета; ClientHello, полученный серверной частью, по-прежнему соответствует исходным данным клиента. Для пересылки сначала используется сплайсинг, а обычная копия откатывается в случае сбоя или недоступности.

### Жизненный цикл соединения TCP Peek

После того, как клиентское соединение поступает в `vpso-mux`, оно обрабатывается примерно в следующем порядке:

```text
клиент TCP подключить
  -> vpso-mux accept
  -> recv(MSG_PEEK) Просматривайте только то, что находится в буфере приема ClientHello
  -> из ClientHello Расширенный анализ SNI
  -> нажать SNI Хэюань IP Выбор белого списка backend
  -> dial Внутренний локальный порт
  -> Переслать оригинал в обоих направлениях TCP поток байтов
```

Самое критичное здесь — `MSG_PEEK`. Обычный `recv` возьмет данные из приемного буфера сокета, и первый прочитанный пакет необходимо перезаписать на бэкенд при последующей пересылке; `MSG_PEEK` просто "смотрит" и не смещает позицию чтения. Таким образом, после того, как `vpso-mux` анализирует SNI, TLS ClientHello, отправленный клиентом, все еще остается в исходном буфере сокета. После того как серверное соединение установлено, первый пакет пересылаемых байтов по-прежнему является исходным ClientHello клиента.

Таким образом, TCP Peek не завершается TLS и не расшифровывается посредником:

- Он не хранит, не выбирает и не выдает сертификаты.
- Он не считывает путь HTTP, заголовок, содержимое WebSocket или зашифрованные данные прикладного уровня TLS.
- Сертификаты и обратный прокси-сервер HTTP по-прежнему обрабатываются текущим механизмом обратного веб-прокси; Трафик узла Xray/REALITY по-прежнему обрабатывается локальным входящим соединением Xray/3x-ui.
- Он использует SNI только на этапе открытого текста рукопожатия TLS для маршрутизации четвертого уровня.

### Что вы видите в ClientHello?

TLS При запуске соединения клиент сначала отправит ClientHello. ClientHello по-прежнему представляет собой текстовую структуру, которая обычно содержит расширение `server_name`, которое представляет собой имя домена, к которому хочет получить доступ браузер или прокси-клиент. `vpso-mux` анализирует только эти поля:

```text
TLS record
  -> record type = handshake
  -> handshake type = ClientHello
  -> extensions
  -> server_name extension
  -> hostname SNI
```

Реализация сначала получит около 4 КиБ данных. Если ClientHello не получено полностью, буфер просмотра будет продолжать расширяться до 16 КиБ и контролироваться `timeouts.peek`. По умолчанию скрипт пишет `3s`. Разобранный SNI будет равномерно преобразован в нижний регистр, а точка в конце будет удалена. Например, `Panel.Example.COM.` станет `panel.example.com`. Если данные не TLS ClientHello, ClientHello неполный, SNI отсутствует или сам протокол не содержит SNI, правило для конкретного доменного имени не будет применено, и последующая обработка будет основана на серверной части по умолчанию.

Вот почему это решение подходит для трафика HTTPS/TLS/SNI, но не подходит для перенаправления трафика на основе пути HTTP или содержимого протокола в виде обычного текста. После рукопожатия TLS содержимое уровня приложения зашифровано, и `vpso-mux` не может и не может полагаться на него для определения пути.

### правила маршрутизации

Сценарий генерирует `/etc/vps-optimize/vpso-mux.yaml` на основе общей конфигурации с общей точкой входа 443. Сгенерированные маршруты условно делятся на несколько категорий:

| Источник маршрута | целевой бэкэнд | Использовать ли белый список веб-сайтов |
| --- | --- | --- |
| домен панели | Caddy/Nginx обратный локальный веб-прокси Порт HTTPS | Да, если для доменного имени настроен белый список |
| Обычный веб-сайт/домен обратного прокси | Caddy/Nginx обратный локальный веб-прокси Порт HTTPS | Да, если для доменного имени настроен белый список |
| Старые локальные входящие записи TCP/SNI | Соответствует локальному адресу и порту | Нет |
| Xray Запись управления входящими событиями | Соответствует локальному входящему адресу и порту Xray. | Нет |
| Маскировка REALITY SNI | Локальный бэкэнд по умолчанию Xray/REALITY | Нет |
| Пропущен SNI / Нет SNI / Не TLS | Локальный бэкэнд по умолчанию Xray/REALITY | Нет |

При сопоставлении сначала выполните точное совпадение SNI, а затем выполните сопоставление доменного имени с подстановочным знаком. Подстановочные знаки соответствуют только одному уровню имен субдоменов. Например, `*.example.com` может соответствовать `a.example.com`, но не будет соответствовать `a.b.example.com`. Если веб-маршрут настроен с использованием белого списка, `vpso-mux` проверит исходный IP-адрес клиента перед выгрузкой; если его нет в белом списке, соединение будет перехвачено напрямую. входящее подключение Xray, REALITY, SNI и бэкенд по умолчанию не используют белый список веб-сайтов, чтобы избежать случайного повреждения трафика узла.

### Разница между склейкой и копированием

`vpso-mux` начинает пересылку только после завершения маршрутизации и подключения к серверной части. Существует два режима пересылки:

| режим | метод работы | Подходит для ситуации |
| --- | --- | --- |
| `splice` | Ядро Linux передает данные между сокетами и каналами, чтобы минимизировать копирование состояния пользователя. | Обычный приоритетный путь |
| `copy` | Процесс Go пересылает данные, используя обычные циклы чтения и записи. | Резервный путь, когда соединение недоступно, происходит сбой или закрыто |

Конфигурация по умолчанию:

```yaml
splice:
  enabled: true
  pipe_size: 1048576
  fallback_to_copy: true
```

Другими словами, `vpso-mux` сначала попытается выполнить сварку. Если текущее ядро, состояние сокета или операционная среда не подходят для сращивания, а `fallback_to_copy` — `true`, он автоматически вернется к обычной копии. копирование не является ошибкой, просто ему не хватает оптимизации без копирования; страницу состояния или `copy_fallback` в `status.json` можно использовать для наблюдения за частыми откатами.

Следует отметить, что сплайсинг оптимизирует «пересылку байтов после выбранного бэкэнда» и не меняет логику маршрутизации. Оценка SNI по-прежнему происходит на этапе ClientHello в начале соединения; как только бэкенд выбрана, последующие соединения TCP не будут перенаправляться в зависимости от содержимого.

Путь сращивания также будет контролироваться `timeouts.idle`. `vpso-mux` использует неблокируемую сварку и ожидает событий, доступных для чтения/записи, прежде чем читать и записывать дескрипторы файлов; если в соединении нет данных в течение длительного времени, оно будет закрыто в соответствии с тайм-аутом простоя вместо того, чтобы позволить простаивающему соединению занять подпрограмму пересылки go. Путь копирования продолжает использовать обычные сроки чтения и записи.

### Защита одновременного доступа и обновление статуса

`vpso-mux` имеет встроенную защиту одновременного подключения. Новая конфигурация, сгенерированная сценарием, будет писать:

```yaml
limits:
  max_connections: 4096
```

Старый `vpso-mux.yaml`, даже без поля `limits`, будет автоматически использовать то же значение по умолчанию программой; пользователям не нужно вручную переносить конфигурацию. Если вы действительно хотите отключить это ограничение, вы можете установить для `max_connections` значение `0`, что означает отсутствие ограничения на количество подключений внутри программы.

Медленное рукопожатие также защищено: если клиент не отправляет полный ClientHello в течение времени `timeouts.peek` после подключения, `vpso-mux` закроет соединение вместо того, чтобы перенаправить его на бэкэнд Xray/REALITY по умолчанию. По умолчанию `timeouts.peek` — `3s`, и обычные браузеры и прокси-клиенты не воспримут это изменение.

Состояние работы записывается в `/var/lib/vps-optimize/vpso-mux/status.json`. Новая версия больше не записывает на диск сразу при каждом подключении. Вместо этого он сохраняет счетчик в памяти, регулярно обновляет его и записывает снова перед выходом. На странице состояния будет отображаться текущее количество подключений, верхний предел подключений, количество отклоненных подключений, ошибки набора номера на внутренней стороне, ошибки проверки, тайм-ауты проверки и количество байтов, пересылаемых в двустороннем направлении, что позволяет легко определить, имеет ли место лавина соединений, медленное квитирование или исключение внутреннего порта.

### Индекс маршрута

`vpso-mux` предварительно скомпилирует индекс маршрутизации после прохождения проверки конфигурации. Exact SNI использует запрос карты, а подстановочный знак SNI остается в виде упорядоченного списка; семантика сопоставления остается неизменной, точное соответствие по-прежнему имеет приоритет над сопоставлением с подстановочными знаками, а сопоставление с подстановочными знаками сохраняет порядок в конфигурации. Эта оптимизация не изменит формат `vpso-mux.yaml` и не потребует от пользователей повторного заполнения доменного имени.

Основные преимущества TCP Peek:

- Процесс настройки такой же, как у Nginx Stream. Сохраненное домен, сертификат, бэкенд механизма веб-обратный прокси, белый список веб-страниц и маршрутизация Xray SNI повторно используются во время переключения.
- `MSG_PEEK` только проверяет ClientHello и не использует первый пакет. бэкенд по-прежнему получает исходные данные рукопожатия TLS клиента.
- При пересылке сначала используется сращивание, чтобы уменьшить копирование данных в пользовательском режиме; когда он недоступен, он автоматически возвращается к обычной копии.
- `vpso-mux` — это начальная программа, специально подготовленная для распространения 443 SNI. Статус, журналы, проверка конфигурации и предварительная проверка 8444 — все это вращается вокруг этой ссылки.

`vpso-mux.yaml`, сгенерированный TCP Peek, будет записывать только один элемент привязки в соответствии с адресом привязки Интернета, сохраненным сценарием. По умолчанию `0.0.0.0:443` привязан только к IPv4; Если вам явно нужна запись IPv6, установите адрес привязки Интернета на `::`, а затем заново сгенерируйте конфигурацию, чтобы избежать конфликтов привязки двойного стека, вызванных одновременной записью `0.0.0.0` и `[::]` на одном и том же порту.

```text
Публичная сеть 443
  -> vpso-mux
  -> recv(MSG_PEEK) Посмотреть TLS ClientHello SNI
  -> нажать SNI / whitelist Выберите серверную часть
  -> splice Двусторонняя маршрутизация, Резервный вариант в случае неудачи copy
```

Основные отличия от Nginx Stream:

| Проект | Nginx Stream | TCP Peek + Splice / vpso-mux |
| --- | --- | --- |
| Процесс настройки | Использовать общую конфигурацию с общей точкой входа 443. | Используйте ту же общую конфигурацию с общей точкой входа 443. |
| Процесс поступления | `nginx` | `vpso-mux` |
| SNI Получить | `ssl_preread` | `MSG_PEEK` анализ ClientHello |
| Обработка TLS | Не завершайте TLS | Не завершайте TLS |
| Сертификат | Текущий механизм веб-обратный прокси обрабатывает веб-сертификаты/сертификаты панелей. | Текущий механизм веб-обратный прокси обрабатывает веб-сертификаты/сертификаты панелей. |
| Неизвестно SNI | бэкенд Xray/REALITY по умолчанию | бэкенд Xray/REALITY по умолчанию |
| вперед | Nginx stream proxy | сращивание, резервное копирование при сбое |

Просмотр статуса и журналов:

```text
Главное меню [19 443 центр управления общим входом]
  -> [18] Посмотреть TCP Peek + Splice Журнал
```

Часто используемые диагностические команды:

```bash
systemctl status vpso-mux --no-pager
journalctl -u vpso-mux -n 120 --no-pager
/usr/local/bin/vpso-mux -config /etc/vps-optimize/vpso-mux.yaml -check
```

Если `transfer_mode` отображается как `copy`, это означает, что сращивание не используется или был выполнен откат. Сращивание можно отключить в `/etc/vps-optimize/vpso-mux.yaml`:

```yaml
splice:
  enabled: false
  fallback_to_copy: true
```

## Xray Специальная реализация резервного варианта

Xray Fallback — это особый режим: Интернет-`443` привязан к существующему основному входящему соединению Xray/3x-ui, а HTTPS — резервный вариант к текущему механизму обратного веб-прокси. Этот сценарий не создает, не удаляет и не изменяет внутреннюю конфигурацию входящего соединения 3x-ui/Xray.

```text
Публичная сеть 443
  -> Xray/3x-ui основное входящее подключение
  -> Xray Трафик узла обрабатывается этим мастером.
  -> HTTPS fallback направляется на локальный веб-бэкенд Caddy/Nginx
```

В резервном режиме xray меню `Xray управление входящими подключениями` недоступно для многолокальной входящей разгрузки SNI. Причина в том, что публичный порт `443` был захвачена основной входящей сетью Xray, и сценарий в настоящее время не поддерживает продолжение разгрузки нескольких SNI на несколько локальных входящих Xray в этом режиме. Для нескольких локальных входящих разгрузок Xray используйте режим Nginx Stream или режим TCP Peek + Splice/vpso-mux.

## Переключение и откат

Переключитесь на TCP Peek + Splice:

```text
Главное меню [19 443 центр управления общим входом]
  -> [16] Посмотреть TCP Peek + Splice Статус / 8444 Предполетная подготовка
  -> [17] TCP Peek проверка правил маршрутизации
  -> [5] переключиться на TCP Peek + Splice режим
```

Процесс переключения не будет автоматически загружать цепочку инструментов Go или удаленно компилировать `vpso-mux` в пути переключения `443` в Интернете. Если `/usr/local/bin/vpso-mux` не существует, сценарий отклонит переключение и потребует сначала выполнить проверку перед переключением `8444` для `[16]`. Перед официальным переключением сценарий снова запустит независимую привязку `vpso-mux-preflight.service` к `8444`, чтобы подтвердить, что механизм обратного веб-прокси и локальный бэкэнд Xray доступны; если проверка перед переключением не удалась, Интернет `443` не будет заменен.

Формальное переключение сгенерирует и проверит `vpso-mux.yaml`, создаст резервную копию, изолирует конфигурацию Nginx stream 443, в настоящее время управляемую VPS-Optimize, запустит `vpso-mux` для захвата публичный порт `443` и проверит, что механизм веб-обратный прокси и локальный сервер Xray доступны. В случае неудачи будет предпринята попытка автоматического отката.

Предварительная проверка `8444` выполнит дополнительную проверку матрицы маршрутизации TCP Peek: имя домена панели и имя веб-домена получат цепочку сертификатов через тестовый порт в соответствии с SNI; бэкенд Xray/REALITY по умолчанию, старые записи TCP/SNI и запись `Xray управление входящими подключениями` проверят, доступны ли для подключения соответствующий локальный адрес и порт. Таким образом, такие проблемы, как отсутствие сертификатов, неготовность механизма веб-обратный прокси или непрослушивание локального входящего порта Xray, можно обнаружить до того, как публичная сеть `443` будет официально перенята под управление.

Если текущий сеанс SSH подключен к входному порту, например `443`, сценарий отклонит переключение, чтобы избежать прямого отключения текущего соединения управления. Вместо этого используйте VNC/Serial Console поставщика облака или сначала войдите в систему, используя запретный порт SSH.

Откат предыдущего раунда переключения режима входа:

```text
Главное меню [19 443 центр управления общим входом]
  -> [7] Откатить последнее переключение режима входа
```

Универсальный откат восстанавливает резервную копию до последнего переключения режим входа и подходит для отмены последнего переключения точки входа, вызванного `[3]`, `[4]` или `[5]`. TCP Peek Эта более широкая запись отката также используется, когда откат требуется после переключения.

## Распространенные неисправности

Проверьте текущую сторону, слушающую публичный порт `443`:

```bash
ss -lntup | grep ':443'
```

Переключитесь на TCP Peek + Splice, и вы должны увидеть `vpso-mux`. Если это по-прежнему Nginx, Caddy или Xray, это означает, что отношение входа не было переключено чисто, и рекомендуется немедленно выполнить откат.

Проверьте локальный сервер веб-обратного прокси-сервера TLS:

```bash
ss -lntup | grep ':8443'
systemctl status caddy --no-pager
```

Проверьте локальное входящее подключение Xray/REALITY:

```bash
ss -lntup | grep ':1443'
systemctl status xray --no-pager
```

бэкенд по умолчанию будет использоваться, когда нет TLS, нет SNI, неполный ClientHello или клиентский протокол не включает SNI. Это не ошибка завершения TLS, поскольку ни Nginx Stream, ни `vpso-mux` не расшифровывают и не завершают TLS.

TCP Peek Общие границы:

| явление | Причина | направление обработки |
| --- | --- | --- |
| `no_sni` увеличено в разы | У клиента нет SNI или соединение не стандартное TLS ClientHello | Подтвердите домен клиентского узла/настройки SNI; трафик, отличный от TLS, будет проходить через серверную часть по умолчанию |
| Серверное обращение по умолчанию | SNI не соответствует ни одному маршруту или SNI не удается проанализировать | Проверьте маршруты в `/etc/vps-optimize/vpso-mux.yaml` и фактическом клиенте SNI. |
| Имя веб-домена заблокировано | Этот веб-маршрут настроен с использованием белого списка, и исходный IP-адрес находится за пределами диапазона. | Проверьте белый список веб-сайтов соответствующего доменного имени, не считайте его ограничением узла Xray. |
| `copy_fallback` увеличение | сращивание не используется или откатывается во время операции копирования | Как правило, это не влияет на доступность; Если вам нужно стабильно наблюдать за производительностью, вы можете сначала оставить резервный вариант по умолчанию. |
| `backend_dial_errors` увеличение | SNI Правило сработало, но соединение с целевым локальным сервером не удалось. | Проверьте локальный порт прослушивания Caddy / Xray / 3x-ui. |
| `peek_errors` увеличение | Возникло исключение при анализе или чтении ClientHello | Проверяйте наличие необычных клиентов, сканируйте трафик или слишком длительные рукопожатия. |
| `peek_timeouts` увеличение | Соединение не выдало полный ClientHello в течение периода ожидания. | Проверьте медленные соединения, проверьте трафик или необычных клиентов. |
| `rejected_connections` увеличение | Достигнут лимит подключений, время просмотра истекло или оно заблокировано белым списком | Посмотрите на `recent_errors` и маршрутизируйте попадания, прежде чем решить, следует ли корректировать клиент или лимит подключений. |
| Пересылаемые байты всегда равны 0 | Соединение вошло в точка входа, но не завершило эффективную двустороннюю пересылку. | Объедините попадания по маршруту, ошибки коммутируемого соединения и журналы, чтобы продолжить поиск. |
| Не удалось подключиться к серверной части | SNI Правило выполнено, но локальный внутренний порт не прослушивается или адрес несовместим. | Проверьте, соответствует ли локальный порт прослушивания Caddy/Xray/3x-ui значению, сохраненному в скрипте. |
