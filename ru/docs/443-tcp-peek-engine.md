# Порт 443: режимы входа и принципы работы

VPS-Optimize поддерживает три режима общего публичного порта 443: Nginx Stream, TCP Peek + Splice (`vpso-mux`) и Xray Fallback. Если специальных требований нет, начинайте с Nginx Stream.

`panel.example.com`, `site.example.com`, `node.example.com`, `SERVER_IP`, `8443`, `8444` и `1443` — примеры. Замените их фактическими доменами, IP-адресом сервера и портами, сохранёнными скриптом.

## Выбор режима

| Режим | Как слушают 3x-ui/Xray | Когда использовать |
| --- | --- | --- |
| `nginx-stream` | Панель, подписка и входы Xray слушают локальные порты `127.0.0.1` | Рекомендуемый режим по умолчанию с наиболее полной совместимостью |
| `tcp-peek` | Те же локальные порты, что и в `nginx-stream` | Нужен `vpso-mux` без повторной настройки доменов, сертификатов и маршрутов |
| `xray-fallback` | Один основной вход Xray слушает публичный `443` и отправляет обычный HTTPS на локальный Web-прокси | Цепочка fallback уже настроена и обслуживается вручную |

Публичный порт `443` может слушать только один процесс: `nginx`, `vpso-mux` или основной вход Xray.

## Общая конфигурация

Три режима входа используют один набор общей конфигурации:

- Web-домены, сопоставления backend и сертификаты общие для всех режимов. Белые списки Web-доменов общие только для Nginx Stream и TCP Peek.
- Сертификат по-прежнему использует существующий процесс `acme.sh + Cloudflare DNS API`, не содержит модуль Caddy DNS и не использует `xcaddy`.
- Белый список защищает только Web-домены и не ограничивает трафик узлов Xray.
- Локальным Web-прокси может быть Caddy или Nginx; при смене режима используется то же сопоставление backend.
- В режимах Nginx Stream и TCP Peek белый список проверяется на входе по `SNI + исходный IP`. В Xray Fallback такого входного фильтра нет.
- Если в `/etc/vps-optimize/sni-stack.env` отсутствует `ENTRY_MODE`, старую конфигурацию читают как `nginx-stream`.
- Новые значения режима: `nginx-stream`, `xray-fallback` и `tcp-peek`. Старые варианты `nginx_stream`, `xray_fallback` и `tcp_peek` сохранены только для чтения старых конфигураций.

Общие пути меню:

```text
Главное меню [19 Управление повторным использованием порта 443]
  -> [2] Установить / сменить режим входа 443
  -> [7] Откатить последнее переключение режима входа
  -> [16] Просмотреть журнал текущего входа
```

Точные поля панели, подписки и входов 3x-ui описаны в документе [Порт 443: развёртывание и настройка](443-single-entry.md).

## Стабильная реализация Nginx Stream по умолчанию

Nginx Stream — стабильный режим по умолчанию. Публичная сеть `443` контролируется Nginx stream, а `ssl_preread` используется для чтения SNI в TLS ClientHello, но TLS не завершается и трафик не расшифровывается.

```text
Публичная сеть 443
  -> Nginx stream ssl_preread
  -> panel/site/sub SNI  -> Caddy/Nginx местный Web обратный прокси TLS
  -> Xray/REALITY SNI   -> Xray/3x-ui локальное входящее подключение
  -> unknown SNI        -> По умолчанию Xray/REALITY бэкенд
```

Это рекомендуемый постоянный режим. Он поддерживает полную цепочку Web, REALITY, панели, подписки, белых списков и отката.

## Реализация TCP Peek + Splice/vpso-mux

TCP Peek и Nginx Stream используют одну сохранённую конфигурацию. Не создавайте второй набор доменов, сертификатов, Web-backend, белых списков или маршрутов Xray SNI. Откройте `[2 Установить / сменить режим входа 443]` и выберите TCP Peek. Скрипт при необходимости соберёт `vpso-mux`, проверит конфигурацию и протестирует маршруты на отдельном порту `8444`. Публичный `443` переключается только после успешной проверки.

`vpso-mux` использует `MSG_PEEK`, чтобы прочитать SNI из TLS ClientHello, не извлекая первый пакет из буфера. Backend получает исходный ClientHello. Для передачи сначала используется splice, а при его недоступности — обычный copy.

### Жизненный цикл соединения TCP Peek

После того, как клиентское соединение поступает в `vpso-mux`, оно обрабатывается примерно в следующем порядке:

```text
TCP-подключение клиента
  -> vpso-mux accept
  -> recv(MSG_PEEK) просматривает ClientHello в приёмном буфере
  -> извлекает SNI из расширения ClientHello
  -> выбирает backend по SNI и белому списку исходных IP
  -> подключается к локальному backend
  -> передаёт исходный TCP-поток в обоих направлениях
```

В отличие от обычного `recv`, `MSG_PEEK` не удаляет данные из буфера сокета. После разбора SNI исходный ClientHello остаётся в буфере и передаётся backend без изменений.

Таким образом, TCP Peek не завершается TLS и не расшифровывается посредником:

- Он не хранит, не выбирает и не выдает сертификаты.
- Он не считывает путь HTTP, заголовок, содержимое WebSocket или зашифрованные данные прикладного уровня TLS.
- Сертификаты и обратный прокси-сервер HTTP по-прежнему обрабатываются текущим механизмом обратного веб-прокси; Трафик узла Xray/REALITY по-прежнему обрабатывается локальным входящим соединением Xray/3x-ui.
- Он использует SNI только на этапе открытого текста рукопожатия TLS для маршрутизации четвертого уровня.

### Что вы видите в ClientHello?

TLS При запуске соединения клиент сначала отправит ClientHello. ClientHello по-прежнему представляет собой текстовую структуру, которая обычно содержит расширение `server_name`, которое представляет собой имя домена, к которому хочет получить доступ браузер или прокси-клиент. `vpso-mux` анализирует только эти поля:

```text
TLS record
  -> record type = handshake
  -> handshake type = ClientHello
  -> extensions
  -> server_name extension
  -> hostname SNI
```

Реализация сначала получит около 4 КиБ данных. Если ClientHello не получено полностью, буфер просмотра будет продолжать расширяться до 16 КиБ и контролироваться `timeouts.peek`. По умолчанию скрипт пишет `3s`. Разобранный SNI будет равномерно преобразован в нижний регистр, а точка в конце будет удалена. Например, `Panel.Example.COM.` станет `panel.example.com`. Если данные не TLS ClientHello, ClientHello неполный, SNI отсутствует или сам протокол не содержит SNI, правило для конкретного доменного имени не будет применено, и последующая обработка будет основана на серверной части по умолчанию.

Вот почему это решение подходит для трафика HTTPS/TLS/SNI, но не подходит для перенаправления трафика на основе пути HTTP или содержимого протокола в виде обычного текста. После рукопожатия TLS содержимое уровня приложения зашифровано, и `vpso-mux` не может и не может полагаться на него для определения пути.

### Правила маршрутизации

Сценарий генерирует `/etc/vps-optimize/vpso-mux.yaml` на основе общей конфигурации с повторным использованием порта 443. Сгенерированные маршруты условно делятся на несколько категорий:

| Источник маршрута | Целевой backend | Белый список Web |
| --- | --- | --- |
| Домен панели | Локальный HTTPS-порт Caddy/Nginx | Да, если он настроен для домена |
| Web-сайт или домен обратного прокси | Локальный HTTPS-порт Caddy/Nginx | Да, если он настроен для домена |
| Старые локальные входящие записи TCP/SNI | Соответствует локальному адресу и порту | Нет |
| Запись из управления входами Xray | Соответствующие локальные адрес и порт Xray | Нет |
| Маскировка REALITY SNI | Локальный бэкэнд по умолчанию Xray/REALITY | Нет |
| Неизвестный SNI / без SNI / не TLS | Локальный backend Xray/REALITY по умолчанию | Нет |

Сначала проверяется точное совпадение SNI, затем шаблоны. `*.example.com` совпадает с `a.example.com`, но не с `a.b.example.com`. Для Web-маршрута с белым списком `vpso-mux` проверяет исходный IP до подключения к backend. Маршруты Xray, SNI REALITY и backend по умолчанию не используют Web-белый список.

### Разница между splice и copy

`vpso-mux` начинает пересылку только после завершения маршрутизации и подключения к серверной части. Существует два режима пересылки:

| Режим | Как работает | Назначение |
| --- | --- | --- |
| `splice` | Ядро Linux передаёт данные между сокетами и pipe с минимальным копированием в userspace | Основной путь |
| `copy` | Процесс Go использует обычные циклы чтения и записи | Резервный путь, если splice недоступен, отключён или завершился ошибкой |

Конфигурация по умолчанию:

```yaml
splice:
  enabled: true
  pipe_size: 1048576
  fallback_to_copy: true
```

`vpso-mux` сначала пробует splice. Если ядро или сокет его не поддерживают и `fallback_to_copy` имеет значение `true`, соединение продолжает работать через copy. Это не ошибка, а менее оптимизированный способ передачи. Частоту переходов показывает `copy_fallback` в `status.json`.

Splice влияет только на передачу байтов после выбора backend. SNI анализируется один раз во время ClientHello; содержимое приложения не меняет выбранный маршрут.

Для splice действует `timeouts.idle`: долго неактивное соединение закрывается и не занимает ресурсы бесконечно. В режиме copy используются обычные тайм-ауты чтения и записи.

### Защита одновременного доступа и обновление статуса

`vpso-mux` имеет встроенную защиту одновременного подключения. Новая конфигурация, сгенерированная сценарием, будет писать:

```yaml
limits:
  max_connections: 4096
```

Старый `vpso-mux.yaml`, даже без поля `limits`, будет автоматически использовать то же значение по умолчанию программой; пользователям не нужно вручную переносить конфигурацию. Если вы действительно хотите отключить это ограничение, вы можете установить для `max_connections` значение `0`, что означает отсутствие ограничения на количество подключений внутри программы.

Если клиент не отправил полный ClientHello за время `timeouts.peek`, `vpso-mux` закрывает соединение вместо передачи на backend Xray/REALITY по умолчанию. Сгенерированное значение по умолчанию — `3s`.

Счётчики периодически записываются в `/var/lib/vps-optimize/vpso-mux/status.json` и ещё раз при завершении. Страница состояния показывает активные и отклонённые соединения, лимит, ошибки подключения к backend, ошибки и тайм-ауты peek, совпадения маршрутов и переданные байты.

### Индекс маршрута

`vpso-mux` предварительно скомпилирует индекс маршрутизации после прохождения проверки конфигурации. Exact SNI использует запрос карты, а подстановочный знак SNI остается в виде упорядоченного списка; семантика сопоставления остается неизменной, точное соответствие по-прежнему имеет приоритет над сопоставлением с подстановочными знаками, а сопоставление с подстановочными знаками сохраняет порядок в конфигурации. Эта оптимизация не изменит формат `vpso-mux.yaml` и не потребует от пользователей повторного заполнения доменного имени.

Основные преимущества TCP Peek:

- Процесс настройки такой же, как у Nginx Stream. Сохраненное домен, сертификат, бэкенд механизма веб-обратный прокси, белый список веб-страниц и маршрутизация Xray SNI повторно используются во время переключения.
- `MSG_PEEK` только проверяет ClientHello и не использует первый пакет. бэкенд по-прежнему получает исходные данные рукопожатия TLS клиента.
- При пересылке сначала используется сращивание, чтобы уменьшить копирование данных в пользовательском режиме; когда он недоступен, он автоматически возвращается к обычной копии.
- `vpso-mux` — это начальная программа, специально подготовленная для распространения 443 SNI. Статус, журналы, проверка конфигурации и предварительная проверка 8444 — все это вращается вокруг этой ссылки.

В `vpso-mux.yaml` создаётся один публичный listener. `0.0.0.0:443` принимает только IPv4. Для IPv6 укажите публичный адрес `::` и заново создайте конфигурацию; не добавляйте вручную оба listener на одном порту.

```text
Публичная сеть 443
  -> vpso-mux
  -> recv(MSG_PEEK) читает SNI из TLS ClientHello
  -> выбор backend по SNI и белому списку
  -> двусторонний splice с переходом на copy при необходимости
```

Основные отличия от Nginx Stream:

| Параметр | Nginx Stream | TCP Peek + Splice / vpso-mux |
| --- | --- | --- |
| Процесс настройки | Использовать общую конфигурацию с повторным использованием порта 443. | Используйте ту же общую конфигурацию с повторным использованием порта 443. |
| Процесс поступления | `nginx` | `vpso-mux` |
| Чтение SNI | `ssl_preread` | Разбор ClientHello через `MSG_PEEK` |
| Обработка TLS | Не завершайте TLS | Не завершайте TLS |
| Сертификат | Текущий механизм веб-обратный прокси обрабатывает веб-сертификаты/сертификаты панелей. | Текущий механизм веб-обратный прокси обрабатывает веб-сертификаты/сертификаты панелей. |
| Неизвестно SNI | бэкенд Xray/REALITY по умолчанию | бэкенд Xray/REALITY по умолчанию |
| Передача | Nginx stream proxy | splice с переходом на copy |

Просмотр статуса и журналов:

```text
Главное меню [19 Управление повторным использованием порта 443]
  -> [16] Просмотреть журнал текущего входа
```

Часто используемые диагностические команды:

```bash
systemctl status vpso-mux --no-pager
journalctl -u vpso-mux -n 120 --no-pager
/usr/local/bin/vpso-mux -config /etc/vps-optimize/vpso-mux.yaml -check
```

Если `transfer_mode` отображается как `copy`, это означает, что сращивание не используется или был выполнен откат. Сращивание можно отключить в `/etc/vps-optimize/vpso-mux.yaml`:

```yaml
splice:
  enabled: false
  fallback_to_copy: true
```

## Xray Fallback

В режиме Xray Fallback существующий основной вход Xray/3x-ui слушает публичный порт `443`, а обычный HTTPS отправляет на локальный Web-прокси. VPS-Optimize не создаёт и не изменяет внутреннюю конфигурацию входов 3x-ui/Xray.

```text
Публичная сеть 443
  -> Xray/3x-ui основное входящее подключение
  -> основной вход обрабатывает трафик узла Xray
  -> обычный HTTPS отправляется на локальный Web-backend Caddy/Nginx
```

В этом режиме меню управления входами Xray не добавляет SNI-маршруты к нескольким локальным входам: публичный `443` уже занят основным входом Xray. Если несколько локальных входов должны использовать один порт `443`, выберите Nginx Stream или TCP Peek.

## Переключение и откат

Чтобы включить TCP Peek + Splice:

```text
Главное меню [19 Управление повторным использованием порта 443]
  -> [2] Установить / сменить режим входа 443
  -> [3] TCP Peek + Splice
```

Если `/usr/local/bin/vpso-mux` или Go отсутствует, установщик попытается добавить необходимые инструменты и собрать программу. Затем `vpso-mux-preflight.service` на отдельном порту `8444` проверит Web- и Xray-backend. При ошибке публичный порт `443` не изменяется, а скрипт показывает состояние сервиса и последние журналы.

При переключении скрипт создаёт и проверяет `vpso-mux.yaml`, сохраняет резервную копию, изолирует управляемую конфигурацию Nginx stream, запускает `vpso-mux` на публичном `443` и повторно проверяет локальные backend. При ошибке выполняется попытка автоматического отката.

Проверка `8444` получает цепочки сертификатов для домена панели и Web-доменов, а также проверяет доступность backend Xray/REALITY и сохранённых маршрутов TCP/SNI. Так отсутствие сертификата, неготовый Web-прокси или закрытый локальный порт Xray обнаруживаются до смены публичного входа.

Если текущий SSH-сеанс использует входной порт, например `443`, скрипт отменяет переключение, чтобы не оборвать управление. Используйте VNC/Serial Console провайдера или сначала подключитесь по другому SSH-порту.

Откат предыдущего раунда переключения режима входа:

```text
Главное меню [19 Управление повторным использованием порта 443]
  -> [7] Откатить последнее переключение режима входа
```

Откат восстанавливает резервную копию, созданную перед последней сменой режима. Для возврата после TCP Peek используется тот же пункт `[7]`.

## Распространенные неисправности

Проверьте текущую сторону, слушающую публичный порт `443`:

```bash
ss -lntup | grep ':443'
```

Переключитесь на TCP Peek + Splice, и вы должны увидеть `vpso-mux`. Если это по-прежнему Nginx, Caddy или Xray, это означает, что отношение входа не было переключено чисто, и рекомендуется немедленно выполнить откат.

Проверьте локальный сервер веб-обратного прокси-сервера TLS:

```bash
ss -lntup | grep ':8443'
systemctl status caddy --no-pager
```

Проверьте локальное входящее подключение Xray/REALITY:

```bash
ss -lntup | grep ':1443'
systemctl status xray --no-pager
```

бэкенд по умолчанию будет использоваться, когда нет TLS, нет SNI, неполный ClientHello или клиентский протокол не включает SNI. Это не ошибка завершения TLS, поскольку ни Nginx Stream, ни `vpso-mux` не расшифровывают и не завершают TLS.

TCP Peek Общие границы:

| явление | Причина | направление обработки |
| --- | --- | --- |
| `no_sni` увеличено в разы | У клиента нет SNI или соединение не стандартное TLS ClientHello | Подтвердите домен клиентского узла/настройки SNI; трафик, отличный от TLS, будет проходить через серверную часть по умолчанию |
