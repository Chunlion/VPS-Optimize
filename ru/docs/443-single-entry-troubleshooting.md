# Диагностика общего порта 443

Прежде чем устранять неполадки, запустите:

```text
Главное меню [19 443 центр управления общим входом] -> [13 443 Проверка соединения]
```

Если вы хотите сообщить о проблеме, запустите:

```text
Главное меню [15 Обзор состояния служб] -> [Создание диагностической информации обратной связи]
```

Пожалуйста, уменьшите чувствительность токена, закрытого ключа и ключа подписки, кроме имени домена, прежде чем публиковать их публично.

## Рекомендации по выбору сайта

Добавляя новый веб-сайт, домен обратного прокси-сервера или заполняя REALITY для маскировки SNI, вы должны сначала определить цель. Имя веб-домена может использовать CDN в соответствии с фактическими потребностями, но исходный сайт будет видеть IP-адрес узла CDN; домен REALITY/node требует, чтобы клиент напрямую подключался к VPS, а прокси-сервер Cloudflare не должен быть включен; REALITY должен использовать внешний реальный сайт HTTPS для маскировки SNI.

При первом устранении неполадок вы можете сначала установить для соответствующего доменного имени значение «только DNS/серое облако», чтобы уменьшить переменные ссылок. Это предложение используется для устранения неполадок каналов доступа и не означает, что Orange Cloud напрямую приведет к сбою выдачи сертификата DNS-01.

## Основная команда проверки

Сначала проверьте, соответствует ли положение прослушивания ожидаемому:

`8443`, `1443`, `40000` и `2096` в следующих командах и примере вывода являются примерами портов; фактическая конфигурация зависит от текущей привязки службы и конфигурации, сохраненной сценарием.

```bash
ss -lntp | grep -E ':443|:8443|:1443|:40000|:2096'
nginx -t
caddy validate --config /etc/caddy/Caddyfile
systemctl status nginx --no-pager
systemctl status caddy --no-pager
```

публичный порт `443` должна контролироваться только службой единого входа, соответствующей текущему `ENTRY_MODE`:

```text
nginx-stream   -> nginx
xray-fallback  -> xray / 3x-ui / x-ui управляемый Xray
tcp-peek       -> tcppeek / vpso-mux
```

Если `/etc/vps-optimize/sni-stack.env` не имеет `ENTRY_MODE`, сценарий считается совместимым с `nginx-stream`. Другие локальные бэкэнды примерно должны быть такими:

```text
127.0.0.1:8443    caddy
127.0.0.1:1443    x-ui / 3x-ui / xray
127.0.0.1:40000   x-ui / 3x-ui
127.0.0.1:2096    x-ui / 3x-ui
```

## ERR_TOO_MANY_REDIRECTS

### явление

Браузер сообщает, что слишком много перенаправлений, и страница панели продолжает прыгать.

### Распространенные причины

- Панель 3x-ui по-прежнему включена и поставляется с HTTPS.
- Caddy меняется на бэкэнд HTTPS, но бэкэнд вынужден вернуться к HTTPS.
- Cloudflare Включить прокси или несоответствие шаблона SSL.

### проверить команду

```bash
curl -I https://panel.example.com/panel/
curl -I http://127.0.0.1:40000/panel/
```

### Решение

- Очистите путь сертификата панели 3x-ui и перезапустите панель.
- Позвольте механизму веб-обратного прокси-сервера выполнить обратный прокси-сервер для локального бэкэнда HTTP.
- 443 Доменные имена, связанные с общей точкой входа, рекомендуется использовать только DNS / Grey Cloud.
- Если вы только что очистили сертификат, а браузер все еще зацикливается, попробуйте еще раз в окне инкогнито.

### Связанный пункт меню

## ERR_EMPTY_RESPONSE

### явление

Браузер выводит запрос `ERR_EMPTY_RESPONSE`, и страница не возвращает содержимое обычным образом.

### Распространенные причины

- Доступ к внутренним портам, таким как `:8443`, `:1443`, `:40000`, осуществлялся.
- SNI пропускает Caddy, и трафик падает до REALITY.
- Текущий режим входа SNI/Маршрут имени веб-домена не включает имя домена панели или веб-сайта; для `nginx-stream` см. конфигурацию Nginx stream, а для `tcp-peek` см. конфигурацию `vpso-mux`.

### проверить команду

```bash
grep -n "panel.example.com" /etc/nginx/stream.d/*.conf
grep -n "panel.example.com" /etc/vps-optimize/vpso-mux.yaml
ss -lntp | grep -E ':443|:8443|:1443'
```

Правильный адрес доступа должен быть:

```text
https://panel.example.com/panel/
```

Не посещайте:

```text
https://panel.example.com:8443/
https://panel.example.com:1443/
https://panel.example.com:40000/
```

### Решение

- Убедитесь, что доступ осуществляется по стандартному адресу HTTPS доменного имени без внутреннего порта.
- Убедитесь, что домен панели, подписки или веб-сайта записано в маршрут Web/SNI, используемый текущим режим входа.
- Повторно примените текущую сохраненную конфигурацию 443.

### Связанный пункт меню

```text
Главное меню [19 443 центр управления общим входом] -> [10 Изменить 443 общие параметры] -> [5 Повторно применить сохранённую конфигурацию]
Главное меню [19 443 центр управления общим входом] -> [13 443 Проверка соединения]
```

## ERR_CONNECTION_CLOSED / ERR_SSL_PROTOCOL_ERROR

### явление

Браузер сообщает, что соединение закрыто, или выдает ошибку протокола SSL.

### Распространенные причины

- публичный порт `443` в настоящее время не контролируется службой входа, соответствующей `ENTRY_MODE`.
- Сервер Caddy, 3x-ui, REALITY или старый сервер Nginx вне текущего режима входа вытеснил публичный порт `443`.
- Трафик TLS перенаправляется на серверную часть, которая не должна получать браузер HTTPS.

### проверить команду

```bash
ss -lntp | grep ':443'
systemctl status nginx --no-pager
systemctl status caddy --no-pager
```

### Решение

- Убедитесь, что публичный порт `443` отслеживается только одной входящей службой, соответствующей текущему `ENTRY_MODE`: `nginx-stream` соответствует `nginx`, `xray-fallback` соответствует основному входящему Xray, а `tcp-peek` соответствует `tcppeek` / `vpso-mux`.
- Caddy Используйте `127.0.0.1:8443`.
- Локальные входящие соединения REALITY/Xray, которые не подключены к основному входящему соединению `xray-fallback`, используют локальные привязки, такие как `127.0.0.1:1443`.
- Серверные панели панели и подписки служат только как родной HTTP.

### Связанный пункт меню

```text
Главное меню [13 Диагностика и освобождение портов]
Главное меню [19 443 центр управления общим входом] -> [10 Изменить 443 общие параметры]
Главное меню [19 443 центр управления общим входом] -> [6 Повторно применить текущий режим входа]
```

## Ограничение одновременного подключения портов при случайном повреждении

### явление

Определенный узел, подписка или веб-сайт иногда не могут подключиться, рукопожатие нарушается или только некоторые исходные IP-адреса имеют доступ к Интернету. Исключение `443`.

### Распространенные причины

- Правило connlimit, добавленное этим сценарием, существует в публичный порт `443`.
- Правило считает одновременные TCP-соединения по публичному порту и исходному IP-адресу; оно не различает SNI, входящие подключения Xray/3x-ui, UUID и пользователей.
- Когда несколько веб-сайтов, подписок и узлов используют публичный порт `443`, соединения с одного и того же исходного IP-адреса могут учитываться в лимите.

### Метод проверки

Сначала посмотрите на параграф «Ограничение одновременных подключений к портам» в проверке работоспособности ссылки 443:

```text
Главное меню [19 443 центр управления общим входом] -> [13 443 Проверка соединения]
```

Если в публичный порт `443` есть правило connlimit, добавленное этим сценарием, оно может быть применено только ко всей публичный порт `443` и не может быть точным для определенного входящего SNI, Xray/3x-ui, UUID или пользователя. Не думайте об этом как о точном ограничении для отдельного узла, входящего подключения или пользователя.

### Решение

- Если подтвердится, что неисправность является случайной, перейдите в меню ограничения одновременных подключений к порту, чтобы просмотреть или удалить правило connlimit публичный порт `443`.
- После удаления правила вернитесь к проверке работоспособности ссылки 443, чтобы убедиться, что правило Интернета `443` остается в файлах среды выполнения и персистентности.

### Связанный пункт меню

```text
Главное меню [19 443 центр управления общим входом] -> [13 443 Проверка соединения]
Главное меню [8 Правила брандмауэра] -> [5 Ограничение количества одновременных подключений к порту]
```

## Nginx работает, но 443 не слушает.

### явление

`текущий 443 Статус входа` показывает `режим конфигурации：nginx-stream`, `nginx：Бег`, но не `Публичная сеть 443：не прослушивается`.

Если на странице состояния также отображается старый запрос совместимости имен, например `nginx_stream` или `tcp_peek`, это означает, что сценарий не может безопасно автоматически перезаписать файл. Следуйте инструкциям, чтобы повторно применить текущий режим входа. Скрипт прочитает и запишет `nginx-stream`, `xray-fallback` или `tcp-peek` в соответствии с новым именем.

### Распространенные причины

- `/etc/nginx/stream.d/vps_sni_443.conf` не был регенерирован после изоляции с помощью переключения или процесса отката.
- `/etc/nginx/nginx.conf` на самом деле не загружает `stream { include /etc/nginx/stream.d/*.conf; }`.
- Nginx stream Динамический модуль установлен, но основная конфигурация не загружает каталог модуля.

### Решение

Первый запуск:

```text
Главное меню [19 443 центр управления общим входом] -> [6 Повторно применить текущий режим входа]
```

Повторное применение приведет к принудительной генерации конфигурации Nginx Stream и проверке того, что `nginx -T` действительно загружает `/etc/nginx/stream.d/vps_sni_443.conf`. Если это по-прежнему не удается, сценарий печатает статус Nginx, последние журналы, включение потока и подсказки привязки порта.

## 404

### явление

Панель, подписка или ссылка Clash/Mihomo возвращают 404.

### Распространенные причины

- Путь доступа не соответствует `webBasePath` или 3x-ui.
- Префикс пути подписки написан неверно, например `sub` вместо `/sub/`.
- Конфигурация Caddy не содержит соответствующего пути.

### проверить команду

```bash
curl -I https://panel.example.com/panel/
curl -I http://127.0.0.1:40000/panel/
curl -I http://127.0.0.1:2096/sub/
grep -R "panel.example.com" /etc/caddy/conf.d /etc/caddy/Caddyfile 2>/dev/null
grep -n "path" /etc/caddy/conf.d/panel.example.com.caddy
grep -n "reverse_proxy" /etc/caddy/conf.d/panel.example.com.caddy
```

### Решение

- Единый путь к панели, например `/panel/`.
- Единый путь подписки, например `/sub/`, `/clash/`.
- 443 Мастер заполняет префикс пути. Не заполняйте `Subscription` клиента вместе.
- Повторно примените конфигурацию 443.

Например, когда Clash/Mihomo использует `/clash/`, три места должны совпадать:

```text
3x-ui URI путь (Clash)：/clash/
443 волшебник Clash/Mihomo префикс пути：/clash/
https://panel.example.com/clash/ПОДПИСКА_КЛИЕНТА
```

При использовании только `/clash/` вы должны увидеть аналогичную конфигурацию в Caddy:

```text
@sub path /clash /clash/*
handle @sub {
    reverse_proxy 127.0.0.1:2096
}
```

Если используются как обычная подписка, так и Clash/Mihomo, `@sub path` должен содержать оба пути:

```text
@sub path /sub /sub/* /clash /clash/*
```

После изменения Caddy вручную не забудьте проверить и перезагрузить:

```bash
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy || systemctl restart caddy
```

## 502

### явление

Браузер может подключиться к HTTPS, но на странице отображается 502.

### Распространенные причины

- Caddy Запрос может быть получен, но бэкенд панели или подписки не работает.
- Внутренний порт прослушивания и конфигурация сценария несовместимы.
- Доступ к пользовательскому веб-сайту/обратный прокси Docker или внутреннему адресу интрасети невозможен с хоста, на котором расположен Caddy/Nginx.
- Бэкенд привязывает только интернет-адрес или только IPv6.

### проверить команду

Для серверной части интрасети замените пример адреса фактическим адресом.

```bash
systemctl status caddy --no-pager
ss -lntp
curl -I http://127.0.0.1:40000/
curl -I http://127.0.0.1:2096/
curl -I http://10.0.0.20:3000/
```

### Решение

- Запустите или перезапустите 3x-ui/x-ui.
- бэкенд панели/подписки: фиксированный адрес и порт прослушивания: `Главное меню [19 443 центр управления общим входом] -> [10 Изменить 443 общие параметры]`.
- Пользовательский веб-сайт/обратный бэкэнд: исправлены адрес и порт бэкэнда: `Главное меню [19 443 центр управления общим входом] -> [8 менеджмент Web домены / обратный прокси] -> [3 Изменить бэкенд сайта/обратного прокси]`.
- Повторно примените конфигурацию и выполните проверка состояния.

Если тест работает по реальному серверному адресу, но интернет по-прежнему 502, обычно это Caddy/Nginx. Адрес или порт обратного прокси-сервера не соответствует фактической привязке.

## В ссылке на подписку все еще есть: 2096.

```text
https://panel.example.com:2096/sub/
http://127.0.0.1:2096/sub/
```

## Ссылка на узел все еще имеет: 1443.

### явление

Ссылка на клиентский узел по-прежнему содержит `:1443`, а публичный порт `443` не используется.

### Распространенные причины

- Внешний прокси-сервер не установлен для входящего подключения REALITY старой версии 3x-ui.
- 3x-ui v3.4.0+ из `Hosts / Хост` не устанавливает интернет-адрес и порт для этого входящего соединения.
- домен узла прошло через прокси-сервер Cloudflare, и клиент не может напрямую подключиться к VPS.

### Решение

3x-ui v3.4.0 и новее: Левая боковая панель -> `Hosts / Хост` -> Новый хост:

```text
Входящее подключение: выберите соответствующее подключение REALITY
Адрес: node.example.com или публичный IP-адрес сервера
Порт: 443
Security: то же значение или фактический тип защиты этого входящего подключения
SNI / Fingerprint / ALPN：Поддерживайте фактическое значение входящего и клиентского трафика согласованным
```

3x-ui v3.3.1 и более ранние версии: вернитесь к входному REALITY и установите `External Proxy`:

```text
Тип: то же значение
Адрес: node.example.com или публичный IP-адрес сервера
Порт: 443
```

Если домен узла — Cloudflare, оно должно быть только Huiyun/DNS.

## Заявка на сертификат не удалась

### явление

Caddy или acme.sh не удалось подать заявку на получение сертификата, а HTTPS не удалось нормально открыть.

### Распространенные причины

- У токена API Cloudflare недостаточно разрешений.
- Токен не авторизует зону, в которой находится текущее домен.
- Запись `_acme-challenge` TXT не была распространена или остаточная запись ненормальна.
- Время сервера неверное.

### проверить команду

```bash
date -Is
dig +short A panel.example.com @1.1.1.1
systemctl status caddy --no-pager
```

## Порт 443 занят

### явление

Nginx не может запуститься, отображается запрос `bind() to 0.0.0.0:443 failed`.

### Распространенные причины

- Caddy, Apache, старый сервер Nginx, 3x-ui или Xray вне текущего режим входа по-прежнему прослушивают публичный порт `443`.
- В режиме `nginx-stream`/`tcp-peek` REALITY напрямую привязан к `0.0.0.0:443` без перехода на локальную привязку.

### проверить команду

```bash
ss -lntp | grep ':443'
systemctl status nginx --no-pager
systemctl status caddy --no-pager
```

### Решение

- Пусть публичный порт `443` передает только одну входную услугу, соответствующую текущему `ENTRY_MODE`; при переключении на `nginx-stream` это Nginx stream, при переключении на `tcp-peek` это `vpso-mux`, а при переключении на `xray-fallback` это основной входящий сервис Xray.
- Caddy заменяется на `127.0.0.1:8443`.
- Локальные входящие соединения REALITY / Xray, которые не являются основными входящими соединениями `xray-fallback`, заменяются на такие локальные привязки `127.0.0.1:1443`.

## Caddy/Nginx/REALITY неправильный адрес прослушивания

### явление

Проверка работоспособности показывает, что служба привязана к Интернету или что ссылка открыта, но внутренний порт открыт.

### Распространенные причины

- Caddy контролирует `0.0.0.0:8443`.
- бэкенд панели привязана к `0.0.0.0:40000`.
- REALITY контролирует публичный порт `443` и конфликтует с Nginx stream.

### проверить команду

```bash
ss -lntp
grep -R "listen" /etc/nginx /etc/caddy 2>/dev/null
```

### Решение

- Локальное прослушивание механизма веб-обратный прокси, панель/подписка 3x-ui и входящие Xray/TCP/SNI продолжают использовать локальные адреса, такие как `127.0.0.1`.
- Пользовательский сайт или бэкенд обратного прокси по умолчанию использует `127.0.0.1`. Для службы во внутренней сети укажите её внутренний IP-адрес или имя хоста, напрямую доступное с текущего VPS.
- Повторно примените конфигурацию 443.
- Сохраняйте SSH и публичный порт `443` при ужесточении брандмауэра.

- REALITY выдает себя за SNI, используя внешний реальный сайт HTTPS.
- домен узла остается только DNS/серое облако.
- Повторно примените конфигурацию 443.
