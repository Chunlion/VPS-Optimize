# dog.sh Traffic Monitor

`dog.sh` is an auxiliary script used to view port traffic statistics, quotas and speed limits.

## Functional positioning

It is suitable for observing usage by port, setting usage limits, limiting bandwidth, and querying or receiving scheduled port-traffic reports through Telegram.

It relies on system components to work, mainly including:

- `nftables counter`: Record the traffic count matched by the monitored port.
- `tc`: Implement port-related speed limit.
- `cron`: Perform boot recovery, scheduled save, daily snapshot and reset check.
- `conntrack`: Auxiliary connection status related processing.
- `ss`, `jq`, `bc`, `curl` and other tools: for ports, JSON, unit conversions and downloads.

It is suitable for port-level monitoring and is not equivalent to VPS merchant bill traffic. Merchant bills are usually calculated by network card, virtualization platform or billing system, and the caliber is different from this tool.

## Quick to install/run

Run as `root` on the server:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Chunlion/VPS-Optimize/main/dog.sh)
```

The script requires `root` permissions because it writes `nftables`, `tc`, and `crontab`. After installation, you can usually use shortcut commands:

```bash
dog
```

It is recommended to retain the current SSH session before running; export the configuration or create a VPS snapshot before modifying quotas, speed limits, resetting or uninstalling on the production machine.

## Description of statistical caliber

- The traffic statistics of `dog.sh` come from `nftables counter`.
- The statistics are TCP/UDP `input` / `output` / `forward` traffic matched by the monitored port.
- The displayed total amount is usually `input + output`.
- It is not the total traffic at the network card level, nor is it the merchant bill-level statistics.
- Traffic on non-monitoring ports will not be counted.
- Scenarios such as loopback, intranet, Docker, forwarding, packet retransmission, platform-side encapsulation or merchant billing rules may cause the results to be different from the VPS merchant panel.

Therefore, it is not recommended to use the results of `dog.sh` for accurate reconciliation with the VPS merchant panel. It is more suitable for observing port-level trends and doing port-level control.

## accuracy bounds

- Real-time port accumulation is suitable for reference, provided that the corresponding `nftables` counter and chain rules exist and have not been cleared, rebuilt, or overwritten by other tools.
- A real-time summary reads every port from one nftables JSON snapshot and validates the counters and rule counts. Missing or duplicate rules are reported instead of being sent as zero usage.
- Daily trends are based on scheduled snapshot increments and may have hour-level cross-day errors.
- Missing calculations or rollbacks may occur due to restart, abnormal power outage, loss of kernel count, or failure to persist in time before script exit.
- Port segment statistics are range aggregations and do not distinguish the individual usage of each port within the range.
- Counts may differ from expectations if Docker, forwarding, NAT, or other network components rewrite the traffic path.
- It is not recommended to use it for precise reconciliation with the VPS merchant panel. The merchant backend should still be used as a billing reference.

## Quota and speed limit instructions

Quotas are used for port-level usage control. The script will set quota rules based on the matched port count. After the quota is exceeded, the corresponding port traffic will be restricted according to the current rules.

The speed limit depends on `tc` and only takes effect on the port rules configured and matched by the script. If there is a conflict with network card identification, `tc` rules, or other network tools, the rate limit may not be as expected.

It is recommended to leave a margin for the quota and not get close to the merchant's monthly traffic limit. For example, when a merchant provides 1 TB of monthly traffic, the port quota should not be set to exactly 1 TB. The merchant's statistical caliber is usually larger and may include system updates, panels, Docker images, DNS, probes and non-monitoring port traffic.

## Daily News and Trends

The daily report is generated by `cron` regularly executing the snapshot task. The current script will collect the current port counter hourly, make an incremental difference from the last snapshot, and write it into the daily report file.

Common reports include:

- Yesterday's report.
- Report on specified date.
- Trends over the past 7 days.

These reports are suitable for viewing trends, not strict splitting of bills from `00:00:00` to `23:59:59`. The cross-day boundary depends on the execution time of the scheduled snapshot, and there may be a snapshot interval error.

## Common operations

- Add port monitoring: Enter `1. Add/remove port listening`, select add port, support single port, multiple ports and port segments.
- Delete port monitoring: Enter `1. Add/remove port listening` and select delete port.
- Set quota: Enter `2. Quota/speed limit management` and set the monthly traffic quota for the port.
- Set speed limit: Enter `2. Quota/speed limit management` and set bandwidth limit for the port.
- View daily reports: Enter `8. Daily and trend reports`.
- Telegram query: Enter `7. Notification management (Telegram Query/Notification)`, deploy the interactive query bot, and use `/t`, `/all`, `/yday`, `/trend`, or `/day YYYY-MM-DD`.
- Telegram notifications: Send a real-time summary immediately or schedule it hourly, every 6 or 12 hours, or once a day at a selected Beijing-time hour.
- Notification template: The built-in template is used by default. Custom templates support `{server_name}`, `{report}`, and `{time}`, and must contain `{report}`.
- Update script: Enter `5. Check and hot update scripts`.
- Uninstall script: Enter `6. uninstall script`. It is recommended to export the configuration before uninstalling.

## file path

| path or location | Description |
|---|---|
| `/etc/port-traffic-dog/config.json` | Main configuration file, including port, quota, speed limit, Telegram and other configurations |
| `/etc/port-traffic-dog/logs/traffic.log` | log file |
| `/etc/port-traffic-dog/traffic_data.json` | Exit or restore associated live count backups |
| `/etc/port-traffic-dog/daily_usage.json` | Daily cumulative data |
| `/etc/port-traffic-dog/daily_snapshot_state.json` | Daily snapshot status |
| `/usr/local/bin/port-traffic-dog.sh` | Local script path, used for scheduled tasks if it exists |
| Dog related tasks in `crontab` | Boot recovery, `--save-data`, `--daily-snapshot`, `--daily-reset-check`, `--scheduled-notify`, and other tasks |

View current scheduled tasks:

```bash
crontab -l | grep -E 'port-traffic-dog|dog.sh|--save-data|--daily-snapshot|--daily-reset-check|--scheduled-notify'
```

## Troubleshooting

### `dog` cannot start

Confirm whether the shortcut command exists:

```bash
command -v dog
```

You can also rerun the remote script directly:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Chunlion/VPS-Optimize/main/dog.sh)
```

If you are prompted for permission issues, switch to `root` first:

```bash
sudo -i
```

### Missing `nft` / `tc` / `ss` / `jq` / `bc` / `conntrack`

The script will try to install dependencies automatically. If the installation fails, first confirm that the system package manager is available and the software source is normal, and then manually install the corresponding package. Common Debian/Ubuntu packages include `nftables`, `iproute2`, `jq`, `bc`, `curl`, `cron`, and `conntrack`.

### Traffic is always 0

Priority checks:

- Whether the port has been added to the monitoring list.
- Whether the service actually sends and receives TCP/UDP traffic on this port.
- Does `nftables` counter exist.
- `input` / `output` / `forward` Whether there is a corresponding counter rule in the chain.
- Is there any other firewall script that rebuilds the nftables table.

Statistical health checks are available in the menu; if counter or chain rules are missing, monitor rules are reapplied.

### Statistics decrease after restarting

Possible reasons:

- The count is not saved to `/etc/port-traffic-dog/traffic_data.json` in time before restarting or powering off.
- `nftables` counter was cleared by the system or other scripts.
- The boot recovery task was not executed.

It is recommended to check `crontab`, `traffic_data.json` and logs. In important quota scenarios, do not set the threshold too close to the merchant's traffic limit.

### Daily newspaper has no data

Check:

- Is `cron` running?
- Whether the `--daily-snapshot` task exists in `crontab`.
- Whether `/etc/port-traffic-dog/daily_usage.json` exists and JSON is valid.
- Monitor the port for actual traffic.

### Scheduled Telegram notification is not received

Check the Telegram Bot Token, Chat ID, `cron` service, and `--scheduled-notify` task. Logs are written to `/etc/port-traffic-dog/logs/traffic.log`. A notification is cancelled when the statistics health check finds a missing counter or duplicate rules, so invalid numbers are not sent.

### Quota is not in effect

Check:

- Whether the port has been monitored.
- Whether the quota is set for the current port.
- `nftables` quota and counter rules exist.
- Are there any other firewall tools that are overriding the script rules?

Quotas only take effect on port rules matched by the script.

### Speed limit is not in effect

Check:

- Does `tc` exist.
- Is the default network card identification correct?
- Whether the port has monitoring rules.
- Are there other scripts or panels that modify `tc` at the same time?

The rate limit only takes effect on the port rules configured and matched by the script.

### Inconsistent with merchant panel

This is expected and common. `dog.sh` is port-level statistics, and the merchant panel is usually complete machine or platform bill-level statistics. Non-monitoring ports, system updates, Docker image pull, panel communication, probes, DNS, intranet forwarding, loopback, retransmission packets and platform side billing rules may all cause differences.

The merchant backend is still the final bill reference.

## Uninstall and clean up

Enter the menu `6. uninstall script` to uninstall. Uninstalling will delete the currently running `nftables` rules, `tc` speed limit, `cron` tasks and configuration file related content. Before uninstalling, it is recommended to export the configuration and confirm that there is a VPS snapshot or other rollback means.

If the script isolates the old configuration to a directory like `/root/port-traffic-dog-quarantine`, make sure it is no longer needed before cleaning it manually.
